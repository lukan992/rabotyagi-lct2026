## Связь активности и плана в 0.4.0 (2026-09-27)

`work_progress.summarize()` формирует детерминированный `work-progress-result-v1` по плану, итоговым VLM-группам, оценке техники и последним sourced progress. API прикрепляет его при включении equipment_activity и сохраняет `versions.work_progress_rules_version=equipment-work-progress-v1` до/после обработки. Новый объект необязателен в общей схеме v1, но обязателен для свежего результата включённого расширения; семантический валидатор сверяет его целиком с исходными источниками. Старые сохранённые ответы выдаются без перерасчёта.

API вычисляет предварительный assess после валидации/claim, до расчёта работы. `ignored_idle_refs()` выбирает current/history detection-пути из возможного простоя с временем ≥stationary_since, сохраняя более раннюю границу изменения. deterministic.analyze получает эту оценку и передаёт исключения в transition; они применяются к конкретным detections, не всему классу. Ранжирование и CV-evidence также исключают только текущие idle detections. schedule не использует bbox и остаётся прежним. Без расширения исключения пусты и результат прежний.

VLM-адаптер передаёт компактные предварительные состояния по detection_id в model_case.equipment_activity; дополнительная инструкция frame-контракта запрещает выводить активность по possible_idle и готовность/отставание по bbox. Обычный VLM → LLM вызов не дублируется. Итоговый assess учитывает прямые supports-ссылки групп с operation_indicated, затем строится work_progress. VLM сохраняет визуальные presence-кандидаты как контекст; work_progress различает их и признаки операции.

Пункты work_progress упорядочены по sequence_no. Совместимые машины берутся по положительным equipment-связям матрицы с учётом object_type; в выбранной VLM-группе остаются только её прямые CV supports. Приоритет: no_class → not_visual; операция группы → operation_indicated; движение совместимой машины → equipment_movement_indicated; только idle-машины → possible_inactivity; присутствие/неопределённость → presence_only; без признаков → insufficient_evidence. Операция машины другой группы не становится признаком движения для иной совместимой работы. Один сигнал может оставаться неоднозначным для нескольких пунктов; счётчики кандидатов не означают число фактических операций.

confirmed_state/confirmed_at/progress_evidence_refs отражают latest_progress без изменения исходного плана. Число completed-пунктов не является взвешенным объёмом или процентом готовности. Новые признаки у completed-пункта дают activity_after_sourced_completion. Выход включает квалификацию кандидата, supporting/ignored/uncertain detection-ссылки, ссылки на activity/VLM, объяснение, список исключений и фактический next_stage_status. Без плана/привязки участка status no_plan/scope_unknown и steps=[]; нет источников/сигналов — insufficient_evidence. Нормативной точности на камерах пока нет. Новых зависимостей, миграций БД и env-параметров не требуется.

## Оценка bbox в пакете 0.4.0 (2026-09-27)

`construction_analytics/equipment_activity.py` вычисляет предварительную оценку до deterministic/VLM и финальную после анализа в существующем `POST /v1/analyze/frame`. Вход включает необязательный объект `equipment_activity` версии `equipment-activity-options-v1`; его отсутствие сохраняет прежнюю форму ответа. Включение добавляет объект результата `equipment-activity-result-v1`, work_progress и `versions.equipment_activity_rules_version=bbox-equipment-activity-v1`. `GET /v1/capabilities?include_extensions=true` сообщает `extensions=["equipment-activity-v1"]`; обычный запрос capabilities сохраняет прежний набор полей. Точная структура, границы параметров и nullable-поля заданы канонической и идентичной пакетной JSON Schema. Настройки и пример подключения: [construction_analytics/README.md](construction_analytics/README.md).

Алгоритм проходит наблюдения текущей камеры от новых к старым. Постоянные `track_id` сопоставляются точно вместе с классом; без них допустимые пары определяются классом, IoU, смещением центра и изменением размера. Принимаются только взаимно однозначные пары, включая ненадёжные detections как конкурентов идентичности. Смешивать внешний ID с геометрическим сопоставлением нельзя. Центры нормализуются по средним ширине/высоте сравниваемых bbox; размер сравнивается относительным изменением ширины/высоты. Каждый исторический bbox сравнивается с текущим, чтобы накопленный медленный сдвиг не исчезал за допуском соседних кадров.

Последовательность прекращается на первом превышении геометрического допуска, пропуске сопоставления, недоступном CV, низкой уверенности, временном разрыве или границе рабочего периода. Используется только непрерывная подтверждённая наблюдениями часть до текущего кадра. `last_change_at` — время более нового снимка на границе обнаруженного изменения, а не точное время физического движения. По умолчанию: idle 14400 с, gap 1800 с, минимум 3 наблюдения, confidence 0.5, допуск центра 0.1 размера bbox, размера 0.2; association IoU 0.1 либо центр ≤1.5 при размере ≤0.6. Все настройки сохраняются в `parameters`, возможны пороги по классам. `camera_stable`, список допустимых классов и рабочий период относятся к политике источника; камера автоматически не стабилизируется.

`possible_idle` требует рабочий период с `source_ref`, разрешённый класс, полный снимок истории и достаточно длинную надёжную неподвижную цепочку. Признак текущей VLM-операции с `supports`-ссылкой на конкретный detection имеет приоритет; оценка операции остаётся групповой. История других камер, исчезнувшие машины, разрывы, ночь и неизвестный график не подтверждают простой. Семантический валидатор проверяет конфигурацию, уникальность tracking ID и времён камеры, происхождение ссылок и ограничения idle; некорректный вход отклоняется до сохранения/модельных вызовов.

Результат содержит по машине статус, причины, оба счётчика наблюдений, границы времени, длительность наблюдаемой неподвижности, максимальные изменения bbox, порог и JSON Pointer-ссылки. Он сохраняется штатным PostgreSQL-журналом вместе с версиями и точными байтами metadata; изменения политики при прежнем ключе дают 409, повтор возвращает сохранённый результат. БД уже хранит JSON-снимки и JSON-ответы, поэтому новая миграция и новые env-переменные не требуются. Исторические изображения/VLM-состояния не запрашиваются. Legacy CLI не включает это HTTP-расширение. Архивные образы/ZIP 0.2.0 не пересобирались.

Проверки алгоритма используют явно тестовые временные последовательности; HTTP-проверки обоих сервисов используют настоящую PostgreSQL и локальный протокольный gateway для VLM-ветки. Это проверка поведения и контрактов, не измерение точности распознавания/простоя на реальных камерах.

## Релиз 0.2.0 (2026-09-26)

Форма frame-analysis-v1 и данные справочников сохранены. Семантический валидатор допускает concrete/no_class и отклоняет summary/неизвестные ID; stage_kind берётся из каталога. deterministic исключает no_class из визуального ranking, сохраняет оценку срока по sourced progress. Проверка transition сначала ищет незавершённые no_class до выбранного anchor: поздние подтверждения не обходят барьер. Completed-барьеры задают нижнюю границу actual_completed_at, иначе effective_at; более новое незавершённое состояние блокирует переход снова. Отдельные визуальные гипотезы не удаляются.

VLM передаёт полный план/профили, stage_kind и selectable_step_keys; schema enum и validate_decision запрещают no_class. Финальный validate_result также сверяет визуальную допустимость с References. Только no_class/нет плана/неизвестный участок — ветка без gateway; readiness без ключа не меняется. vision_model/llm_model в v1 — настроенная модель, факт отсутствия вызова указан в limitations и нулевом журнале попыток.

CLI bootstrap: миграция 005 → неизменяемый импорт → ограниченные LOGIN-пользователи → проверка чтения через LOGIN + SET ROLE. Требуются ANALYTICS_DETERMINISTIC_DB_PASSWORD и ANALYTICS_VLM_DB_PASSWORD. lct_deterministic_app/lct_vlm_app имеют NOINHERIT и членство только в собственной runtime-роли; приложения не получают административный пароль. Повтор bootstrap обновляет свои пароли и сохраняет историю. export-catalog --output PATH [--service deterministic|vlm_llm] использует тот же References.catalog(), что API.

Dockerfile собирает два target из Python 3.13.12-slim-bookworm. Build context ограничен pyproject.toml и construction_analytics; runtime UID 10001, read-only + tmpfs /tmp. Release Compose содержит PostgreSQL 16.15-alpine (pg_data), одноразовый bootstrap и два HTTP-сервиса. Порты localhost 15432/18001/18002 настраиваются; сети Compose дают приложениям postgres:5432 и доступ к внешнему gateway. Health deterministic проверяет ready, VLM — live, чтобы доступна была безмодельная ветка. Корневой compose.yaml сохранён для прежней локальной БД и не переключает её на релиз.

Архив images/analytics-images.tar включает два приложения и PostgreSQL для Linux/amd64. SQLite/матрица в references — только проверенные источники bootstrap; приложения читают PostgreSQL. Manifest фиксирует image IDs, версии, архитектуру и SHA файлов; SHA256SUMS проверяет комплект. Сборщик не читает .env, рабочую БД или фотографии пользователя. Примеры используют созданную синтетическую иллюстрацию и явно демонстрационные планы/CV/progress.

Контейнерный тест загружает архив, запускает отдельный проект/volume из отдельного каталога, проверяет bootstrap/repeat, каталог/API, LOGIN/RLS, idempotency, сохранность после пересоздания и pg_dump/pg_restore в другой БД. Gateway timeout проверяется только локальным HTTP-стендом. Реальный gateway и внешний адаптер этим не подтверждаются. Подробные результаты — service-release/verification.json. Аудит по-прежнему без автоматической очистки.

Перенос SQLite-профилей в PostgreSQL, HTTP и Docker-поставка реализованы в `construction_analytics` 0.2.0; встраиваемый модуль внешнего бэка остаётся внешним этапом. ## Реализованный контракт интеграции (2026-09-26)

[BACKEND_INTEGRATION.md](BACKEND_INTEGRATION.md) — самостоятельная инструкция агенту внешнего бэка; [contracts/frame-analysis-v1.schema.json](contracts/frame-analysis-v1.schema.json) — JSON Schema Draft 2020-12 для запросов, результатов, ошибок, каталога и capabilities. Обе HTTP-оболочки поддерживают этот интерфейс.

Единица анализа — кадр камеры и один явно привязанный участок. Два `POST /v1/analyze/frame` на разных базовых адресах получают одинаковые файловые multipart-части `metadata` (application/json, filename metadata.json) и `image`. Вход `frame-analysis-input-v1` содержит внешние ID, точные байты/хеш кадра, отдельные CV-детекции с нормализованными xyxy bbox, неизменяемый снимок внешнего плана и историю с границей времени. Отсутствующие CV, план и confirmed progress имеют явную семантику и не заменяются фиктивными данными.

Выход `frame-analysis-result-v1` разделяет `current_work`, `transition` и `schedule`, сохраняет версию плана/каталога/истории и источники. `frame-analysis-error-v1` отделяет ошибку выполнения от недостатка признаков; документ задаёт HTTP-коды, идемпотентность, разрешённые повторы и неопределённое выполнение gateway. Межполевая проверка дат, координат, ссылок и справочников обязательна сверх JSON Schema.

Консервативные правила `schedule-rules-v1` используют sourced progress и фактические времена; отсутствие машины само по себе не даёт отставания. Правила, долговечный журнал и семантические валидаторы реализованы. Старый `llm-stage-input-v1` не переименован: совместимый CLI и новый HTTP-адаптер используют одно ядро с разными явными входами/выходами. Поддержка контракта внешней командой и реальные входы ещё не подтверждены.

| `vision_contract.py`, `vision_schema.py`, `decision.py` | Самостоятельные валидаторы существующего VLM/legacy LLM и нового внутреннего frame-work-groups-v1; экспериментальный код для запуска не нужен. |

### Данные и права

Добавочная `db/005_analytics_services.sql` применена к локальному PostgreSQL; исходные `construction.*` не меняет. `analytics_catalog.rule_set` хранит матрицу и её SHA, `profile_set` — метаданные и полный снимок девяти исходных таблиц, `visual_profile` — точный TEXT каждого из 377 исходных JSON-профилей. Импорт проверяет hash исходной матрицы из metadata, integrity/FK SQLite, ID/иерархию и обратное чтение из PostgreSQL до commit. Повтор импорта той же версии допускается, изменение её содержимого — нет.

Импортированы `construction-class-matrix-v2.0`, `catalog-cf435bba295909ab953facca`, `visual-profiles-708cb01523c740f39b8789aa`. HTTP-каталог публикует 40 equipment-классов; 16 visual-классов остаются справочным содержимым матрицы и не принимаются как внешний CV техники. Исходная SQLite-база и артефакты не удалены, статус профилей не изменён.

`analytics_runtime.image` сохраняет оригинальные байты как BYTEA по SHA; `frame_identity`, `plan_snapshot`, `step_identity`, `history_snapshot`, `progress_identity` проверяют неизменяемость внешних источников. `request` содержит исходный metadata TEXT, image hash, UUID анализа, версии, fingerprint и состояния running/succeeded/failed/unknown. `attempt` содержит VLM/LLM start/response, полный prompt, payload, usage и время. PostgreSQL обеспечивает сохранность при перезапуске приложения; автоматическая очистка пока отсутствует.

Для `(service,site_id,request_id)` транзакционный advisory lock запрещает двойной запуск. Повтор использует исходные байты и возвращает записанный исход, в том числе после смены справочников/ключа модели. Таймаут gateway и HTTP 5xx дают unknown, повтор/lookup — 409 execution_uncertain. Running старше настраиваемого порога тоже становится unknown без повторного вызова. Запись начала попытки происходит до сети. Жёсткий общий watchdog и административный API сверки uncertain-запросов не реализованы; каждый модельный вызов имеет timeout, runtime SQL — statement timeout 15 с и lock timeout 5 с.

Runtime выполняет SET ROLE одной из двух NOLOGIN-ролей, каталог читает без права изменения, пишет только локальные снимки/журнал; RLS разделяет request/attempt по сервису. Прав на старую историю `construction.*` не выдаётся. Локальный администратор используется для миграций; поставке нужны отдельные LOGIN-учётки с членством только в своей роли.

### Границы алгоритмов

HTTP не вызывает старые SQL rank/assess-функции. Ранжирование использует матрицу v2, а алгоритм следующей работы перенесён из assess_next_stage для явного снимка и применяет положительные equipment-связи v2. После sourced reset not_started старые сигналы исключаются. Камеры одного момента дают одну точку; положительный сигнал требует двух точек с интервалом ≥15 минут и полного необходимого окна до семи дней. Матрица v2 и старая SQL-матрица не объявляются идентичными.

`schedule` проверяет последнюю sourced запись каждого пункта: фактическое окончание после дедлайна или открытое состояние после него. Величина задержки относится к моменту источника; состояние до дедлайна не экстраполируется до кадра. VLM schedule/transition не оценивает. Визуальный вывод не записывается как подтверждённый progress. CV history и подтверждения должны быть не позже as_of, recorded_at не раньше effective_at; фактические времена не позже effective_at. Все пункты одной работы сохраняют разные step_key.

## Отдельный контур VLM → LLM

`llm_contour/run.py` — исполняемый CLI без обращения к PostgreSQL-ранжировщику. Вход `llm-stage-input-v1` задаёт один кадр, время с часовым поясом, идентификаторы площадки/участка/версии плана, наблюдения техники и конкретные `plan_steps` с устойчивым `step_key`, порядком, `stage_id` и плановыми датами. Известное состояние пункта требует источника и времени события; неизвестное допустимо. Коды техники проверяются по `class_reference`, ID работ — по существующей SQLite-базе визуальных профилей. Сводные и организационные строки отклоняются как конкретные кандидаты. Подробный контракт и команды — `llm_contour/README.md`.

Фото отправляется через `construction_analytics.gateway`, встроенный `construction-context-v1`, JSON Schema и локальный `vision_contract.validate_payload`; runtime-импортов из `tmp/vision_benchmark/` нет. VLM получает общий визуальный prompt без списка работ из плана. Валидный полный payload, а не только новые коды классов, затем передаётся текстовой LLM вместе с наблюдениями техники, планом и профилями соответствующих работ. Для замеченных классов добавляются условные связи `stage_class_context` из SQLite; профиль и дата плана не считаются наблюдением. Оба вызова используют один model ID: по умолчанию `qwen3.8-27b` из последнего фото-прогона; изменить его можно единым `--model`. Gateway URL задаётся отдельно. Сохранённый VLM-record от другой модели отклоняется. Ключ читается только из `LITELLM_API_KEY` окружения процесса.

Выход `llm-stage-assessment-v2` имеет статус `assessed`, `insufficient_evidence` или `outside_plan`. При `assessed` он содержит массив `work_groups` (до восьми): в каждой группе один `step_key` с `match_status=specific` либо несколько ключей с `match_status=ambiguous`, `visual_state` (`operation_indicated` / `presence_or_result_only`), `area_observation_ids`, ссылки evidence и объяснение. Разные группы означают разные наблюдаемые операции или зоны; несколько ключей внутри группы означают неоднозначность одной операции. Для каждой группы вычисляется охватывающий `area_bbox`, а ключи обогащаются исходным `stage_id`, названием и полным путём работы. Локальная проверка отклоняет отсутствующие в плане ключи, вымышленные ссылки, группы без поддерживающего наблюдения VLM средней/высокой уверенности и несколько групп без отдельных визуальных якорей. Она проверяет ссылки и структуру, но не доказывает семантическую различность операций или их одновременность во времени. Допускается по одному повтору невалидных ответов без локальной правки payload. В новом каталоге сохраняются копия кадра, вход, контекст, попытки VLM/LLM, prompt и результат с хешами. Импорт одного ранее сохранённого валидного VLM-record разрешён только при совпадении `image_id` и SHA-256 кадра. `--check-input` проверяет локальные входы без сети. Результаты старых прогонов сохраняют контракт v1 и не мигрируются автоматически.

Технический сквозной прогон v1 `outputs/llm_contour/2026-09-25-smoke-screenshot-002-qwen27/SMOKE_REPORT.md` выполнен на реальном PNG, синтетических классах техники и явно тестовом плане: VLM и LLM дали валидные ответы в первом запросе, обе использовали `qwen3.8-27b`; LLM вернула `insufficient_evidence` с тремя альтернативами. Для v2 сохранённый проверенный VLM-ответ по Screenshot_48 был повторно передан той же LLM с ручными классами техники и тестовым планом: получена одна группа земляных работ с тремя неоднозначными строками и `presence_or_result_only`. Двух одновременно различимых работ на независимом кадре пока не проверяли; это проверено контрактными тестами на составленном примере. Ключ был временно получен из ранее настроенного Kubernetes Secret, в проект не записывался. В обычном окружении `LITELLM_API_KEY` отсутствует; реальных CV-выходов и календарных планов для benchmark-кадров нет. Поэтому точность фактического этапа не измерена. Одиннадцать локальных контрактных тестов проходят; объединение с детерминированным SQL-контуром остаётся отдельной задачей.

## Эксперимент с vision-контекстом

`VISION_MODEL_REQUIREMENTS.md` задаёт контракт `construction-context-v1` для визуальных наблюдений, состояний, отношений и восьми обязательных проверок, а также правила передачи контекста в сопоставление этапов.

В `tmp/vision_benchmark/run_benchmark.py` реализован отдельный воспроизводимый runner: он извлекает кадры из ZIP, вызывает четыре OpenAI-compatible gateway-модели, проверяет JSON и семантику контракта, замеряет latency, usage и VRAM, затем сохраняет сырые и агрегированные результаты. Для Qwen отключён reasoning через `chat_template_kwargs.enable_thinking=false`; без этого модель может израсходовать весь лимит генерации без итогового payload. `tmp/vision_benchmark/generate_report.py` формирует помодельный и покадровый отчёт, включая снимок размеров checkpoint, capacity planning и оценку стоимости инфраструктуры на зафиксированную дату; эти цены не являются измеренным тарифом gateway.

Полный запуск 20 сентября 2026 года выполнен на 100 кадрах и 400 запросах с concurrency=4. Артефакты находятся в `outputs/vision_benchmark/2026-09-20-full-c4/`, итоговый анализ — в `REPORT.md`. Первоначальный выбор E4B по скорости пересмотрен после визуального аудита: основной кандидат по качеству контекста — `qwen3.8-flash-next`; для конкурентных online-запросов остаётся проблема очереди backend.

`tmp/vision_benchmark/prepare_accuracy_review.py` готовит контактные листы из исходного ZIP; `evaluate_accuracy.py` сопоставляет сохранённые checks с разметкой `accuracy_review/reference_checks.json` и сохраняет подробные решения, метрики и `ACCURACY.md`. Оценщик Codex просмотрел все 100 фотографий; из 800 эталонных позиций 606 определимы, 194 исключены как неоднозначные/недоступные. Для каждой модели рассчитаны precision/recall/F1 и доля корректных checks с учётом отказов. Неопределённость модели не считается подтверждённым отрицанием, пропущенные ответы не получают балл. Смысловая проверка использует разобранный payload даже при отдельных нарушениях схемы; формат и содержание оцениваются отдельно. Это предварительная разметка одним AI-рецензентом, а не экспертный ground truth. Полы, точность всех описаний и отношений, IoU bbox и качество ранжирования этапов численно не оценены. Интеграция vision в рабочий pipeline и изменения SQL/БД не выполнялись.

Повторный расчёт отчёта без вызовов моделей: `python tmp/vision_benchmark/evaluate_accuracy.py`, затем `python tmp/vision_benchmark/generate_report.py`. Генератор включает раздел аудита при наличии `accuracy_review/ACCURACY.md`.

Второй сравнивает на одних кадрах матрицу v2 с входом только из синтетических классов техники, со всеми синтетическими CV-классами и оба варианта с добавлением новых визуальных классов четырёх моделей из уже выполненного image-прогона. Результат действующей SQL-функции вынесен в справочный раздел и не входит в парное сравнение. Метрики — совместимость семейства работы в top-1/top-3 и в группе равных первых кандидатов с визуальной разметкой одного AI-рецензента, а не точность фактически выполняемой работы или конкретного ID. Прокси-метки и синтетический CV зависимы и не заменяют независимый производственный эталон.

### План и переход к следующей работе

- `plan_stream` задаёт независимый участок внутри `site`; `(site_id, code)` уникален. Необязательный `observation.plan_stream_id` привязывает кадр к участку; составной FK гарантирует, что участок принадлежит той же площадке. Старые наблюдения без участка не используются новым алгоритмом.
- `plan_revision` хранит номер версии в участке, источник, причину изменения, время создания и публикации. `plan_step` содержит полный снимок версии: устойчивый `step_key`, порядковый номер, ID конкретной работы и плановые границы. Время начала по порядку не убывает, конец позже начала; работа должна быть применима к типу объекта. Для замены самой работы нужен новый `step_key`. Публикация — обновление `published_at` у заполненной черновой версии; триггер выставляет фактическое время публикации и требует следующий номер версии. Опубликованные версии и пункты неизменяемы.
- `plan_step_change` вычисляет добавленные, удалённые и изменённые пункты между соседними опубликованными версиями по `step_key`. `plan_progress_event` хранит добавляемые без редактирования утверждения `not_started`, `in_progress`, `completed` с временем действия, временем записи и источником. Событие ссылается на пункт опубликованной версии. Для исправления записывается новое событие; текущим считается последнее по времени действия и записи. Эти записи являются введённым/подтверждённым контекстом, не результатом распознавания.
- `assess_next_stage(plan_stream_id, as_of, window, min_observations, min_separation)` выбирает последнюю опубликованную на `as_of` версию. Позиция берётся из самого дальнего пункта с актуальным событием `in_progress` или `completed`; без события возвращается `needs_progress_anchor`. Проверяется только следующий по `sequence_no` пункт. Вычисляется разность классов `stage_equipment(next) − stage_equipment(current)`; совпадающие машины не свидетельствуют о переходе. При пустой разности возвращается `not_distinguishable_by_equipment`.
- Наблюдения в том же участке учитываются после времени подтверждённой позиции, в окне по умолчанию 7 дней. Обновление плана не стирает более ранние наблюдения об устойчивом `step_key`. Не менее двух наблюдений с отличительным классом, разделённых не менее чем 15 минутами, дают `possible_start`; `evidence_first_at` — первое обнаружение в этом окне, **не установленное время фактического начала**. Плановые даты выводятся как контекст, но не используются как доказательство начала. ### Проверка приблизительных областей на датасетах

`outputs/camera_overlap_datasets_2026_09_26/overlap_validation/REPORT.md` описывает последующий реальный эксперимент: 42 изображения семи последовательностей HPatches (35 пар одной сцены и 21 межсценовая), все 21 пары семи камер WILDTRACK, 66 пар 12 равномерно выбранных из 38 фото ETH3D courtyard, 45 пар прежних строительных фото. `download_public.py` извлекает выбранные HPatches через HTTP Range/ZIP CRC32 из закреплённой ревизии, скачивает официальный полный архив undistorted courtyard и извлекает все 38 JPEG/два файла калибровки (`py7zr==1.1.3` в локальном demo-окружении), получает 14 XML WILDTRACK с проверкой Git blob IDs закреплённого зеркала. `benchmark.py` проверяет F/H с USAC_MAGSAC при масштабе длинной стороны 1024 (пороги 2/3 px), затем выделяет маски 512 px и контуры в исходных координатах. Базовый фильтр требует ≥30 inliers/долю ≥0.45/оболочку ≥1%; консервативный — ≥50 при остальных тех же условиях. Для консервативного варианта перенос границы всего кадра по H разрешён только в предполагаемой плоской сцене HPatches; объёмные сцены получают область поддержки локальными треугольниками/окрестностями соответствий. При отказе маски пустые; отказ не доказывает отсутствие пересечения. Консервативный вариант переиспользует исходные соответствия базового, строительные пары используют сохранённый ранее реальный запуск. Пороги и маски эвристические; второй фильтр выбран на той же подборке после обнаружения слабой ложной пары, независимо не откалиброван.

Каждая пара в `results/` и `results_conservative/` содержит координаты/оценки, F/H, маски, полигоны и превью. Предоставленные H/калибровки применяются только после предсказания для оценки. В HPatches выдано 32/35 положительных кандидатов, 0/21 отрицательных; для 28 плоских пар медиана IoU с масками предоставленной H 0.9995. В WILDTRACK консервативный фильтр оставляет три кандидата; базовый C1–C2 был ошибочным (0% эпиполярного согласия выбранных точек). ETH3D даёт 44 кандидата, у 15 из них менее 10% точек согласуется с калибровкой при пороге 3 px/1024: повторяющиеся фасады дают сильные ложные связи. Это диагностика соответствий, не точность пиксельных зон. На стройке получены две области вокруг общих ориентиров; независимой разметки покрытия нет.

`validate_artifacts.py` проверяет манифесты, хеши/границы/маски всех 376 результатов, неизменность соответствий двух вариантов и COLMAP-конвенцию на предоставленных SfM-треках (не пиксельный GT). `build_report.py` строит метрики, отчёт и `.lavish/camera-overlap-validation.html` с локальными превью и фильтрами. ### Самостоятельный модуль пересечений 0.1.0

`camera_overlap_module/` — отдельный setuptools-проект `lct-camera-overlap`, Python 3.11–3.13; пакет `camera_overlap`, CLI `camera-overlap`/`python -m camera_overlap`. Зависимости закреплены на проверенных Torch 2.7.1, NumPy 2.1.2, Pillow 12.2.0, Kornia 0.8.3, OpenCV 5.0.0.93. Два файла SuperPoint/LightGlue с прежними SHA-256 включены в wheel. Выбранные upstream-файлы и исходные notices/лицензия сохраняются в `_vendor` с commit/хешами; SuperPoint изменён только для обязательной локальной загрузки. LightGlue создаётся с `features=None`, локальные ключи переименовываются по upstream-процедуре; допускаются только известный вычисляемый buffer и девять устаревших скаляров release. Сеть, torch.hub cache, зависимости на experiment/vendor paths и глобальные настройки потоков не используются при анализе.

`OverlapDetector(weights_dir=None, device='auto', config=OverlapConfig())` загружает модели один раз. `analyze(image0, image1)` принимает пути, bytes/bytearray или PIL.Image; вызовы одного экземпляра сериализованы. Декодирование ограничивает 50 MiB/40 млн пикселей, поддерживает JPEG/PNG/WEBP/PPM/BMP/однокадровый TIFF, применяет EXIF-поворот и сведение прозрачности на белый RGB. Координаты/размеры относятся к изображению после EXIF-поворота. Ошибки ввода, локальных хешей и устройства явные; отсутствие совпадений является измеренным результатом, а не исключением.

По умолчанию используется прежний консервативный F/H/локальный регион-фильтр. Полный перенос плоскости по H допускается только с явным `assume_planar=True` и дополнительными проверками; он не включается на основании названия датасета или количества совпадений. Маски uint8 0/255 около 512 px, `mask_original(i)` даёт размер фото. Контуры содержат exterior/holes в исходных отображаемых пикселях; F предоставляется в исходных и нормализованных координатах, H переносит первое изображение во второе.

`OverlapResult.status` — `candidate_overlap`/`insufficient_evidence`; `to_dict()` соответствует `schemas/result.schema.json` (`camera-overlap-v1`) и содержит метрики/причины, изображения/контуры, параметры/хеши, устройство/время и ограничения интерпретации. `save(directory, overwrite=False)` сохраняет result.json, mask0/1.png, matches.npz и overlap.jpg; непустая папка требует явного разрешения на перезапись параметром. CLI exit 0 — выполненный анализ, включая отказ по поддержке; exit 2 — ошибка. Конструктор может использовать CPU/CUDA, auto выбирает доступный CUDA. Для async-сервиса вычисление нужно вынести из event loop; HTTP-обёртка не реализована.

Проверки: `tests/test_contracts.py` — ввод/EXIF/лимиты, плохие веса, пустая/вырожденная геометрия, явная плоскость и контуры с отверстиями; `scripts/verify_real.py` — реальные веса, все 188 прежних пар, сверка соответствий/масок и JSON-схемы. Пакет собран независимо от корневого аналитического релиза; версия 0.2.0, Docker аналитических сервисов, HTTP/API и БД не менялись. ### Матрица классов v2 для будущего подключения к БД

Актуальная отдельная версия — `outputs/ranking_matrix_v2_2026_09_21/REPORT_v2.md`, `matrix_v2.json` и `Матрица_строительных_классов_v2.xlsx`. Предложение v1 выше сохранено как история исследования; его веса не нужно смешивать с v2. Новая версия `construction-class-matrix-v2.0` включает 377 работ, 56 классов, 84 технологических семейства для всех 313 конкретных работ и 2238 положительных пар (1596 техники, 642 визуальных). Плотное представление определяет 21112 сочетаний строки и класса. 50 сводных строк не являются самостоятельными кандидатами; 14 исходных `no_class` и ещё девять конкретных работ не определяются этими классами. Остальные конкретные работы разделены на 145 с процессными якорями и 159 с контекстом без якоря.

`role_weight` (T) описывает участие в технологии, `signal_weight` (S) — силу признака для текущей работы, `0 <= S <= T <= 3`. T не является прежним `compatibility_weight` C. Все положительные пары развёрнуты из 116 явных правил, без фонового заполнения оставшихся связей единицей. Пересмотрены все 424 старые пары техники с A=1 (347 имели автоматическое фоновое основание). Для старой очереди 310 пар зафиксированы 203 включения и 107 отказов; 12 старых связей конкретных работ выключены только в предложении v2. Матрица v2 не импортирована в рабочую БД; новый контур плана использует существующие связи 40 классов техники.

JSON содержит классы, псевдонимы, исходные работы/фазы/применимость по типам объектов, положительные пары, плотную матрицу, технологические правила, аудит v1, решения старой очереди, основания и контрольные суммы. На вход локального эталонного расчёта поступает массив кодов, необязательные тип объекта/фаза. `rank_reference.py` удаляет дубли, проверяет коды, использует максимум внутри зависимых групп и сумму трёх основных групп плюс ограниченный фон, возвращает два балла, статус, совпадения, группы альтернатив и лучший конкретный кандидат по фазе. Баллы не являются вероятностями; частота бенча и множители фаз не используются. `phase_id=43` включает дочерние фазы в фильтре, но в сводке конкурирующих фаз запись 43 относится только к непосредственно прикреплённым работам 44/45.

Для интеграции предложен самостоятельный версионированный слой `ranking_rule_set`, `cv_class`, `stage_cv_weight` и статусов покрытия; весовая пара не должна ссылаться на удаляемую при seed запись `stage_equipment`. Поля аудита не импортируются как дополнительные активные связи. Миграция, новый SQL API и переключение потребителя ещё не выполнялись.

Воспроизведение: `python outputs/ranking_matrix_v2_2026_09_21/build_matrix.py`, затем `python outputs/ranking_matrix_v2_2026_09_21/test_matrix.py`. Генератор повторно использует только парсер SQL предыдущего исследовательского скрипта, а веса задаёт независимо. `rank_reference.py` читает готовый JSON и использует стандартную библиотеку Python. Excel создаёт `tmp/ranking_matrix_v2_work/build_workbook.mjs` через bundled `@oai/artifact-tool`; `verify_workbook.py` проверяет сохранённый XLSX по JSON. Для Excel подтверждены пересчёт якорей/покрытия при правке S, отсутствие формульных ошибок, фильтры и закрепление C6. Ручная правка Excel не обновляет JSON автоматически. `.lavish/ranking-matrix-v2.html` — локальная таблица просмотра того же снимка, не источник истины.

20 тестов целостности и поведения проходят. Проверена визуализация всех пяти листов и сохранённые значения XLSX. Нативный Excel не запускался. Нет фактических CV-выходов и независимой разметки работ, поэтому эмпирическая точность не измерена; результат — экспертная матрица для интеграции, а не откалиброванная вероятностная модель.

### Общие ограничения

Соответствия являются кандидатами на основе технологических карт и ПОС, ссылки на которые приведены в XLSX. Эти документы описывают возможные технологии на других объектах и не подменяют ППР наблюдаемой площадки. Примеры из ZIP подтверждают только различимость класса на изображении. Списки классов в одной строке могут включать альтернативы и разнесенные по времени операции.

HTTP API аналитики реализован в `construction_analytics`; собственного CV-детектора и очередей обработки в этом контуре нет. Схема для хранения плана и проверки ближайшего перехода есть, но для вывода о реальном ходе работ нужны фактический график объекта, наблюдения с привязкой к участку и независимое подтверждение активности работ.
