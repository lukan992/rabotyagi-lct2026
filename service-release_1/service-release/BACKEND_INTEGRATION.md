# Контракт интеграции аналитических сервисов с внешним бэком

Ресурсный контракт v2 реализован в аналитике 0.5.0 и описан отдельно: [RESOURCE_INTEGRATION.md](RESOURCE_INTEGRATION.md). Этот документ сохраняет семантику v1.

Версия: `frame-analysis-v1` с необязательным `equipment-activity-v1`. Дата: 2026-09-27.

**Статус: два HTTP-сервиса `construction_analytics` 0.4.0 поддерживают mixed/no_class-планы и включаемую оценку движения/возможного простоя. Архивные Docker-образы 0.2.0 не содержат расширения активности. Адаптер внешнего бэка и совместный прогон остаются внешним этапом.** Комплект запуска 0.2.0: service-release/README.md (путь в исходном репозитории: `service-release/README.md`). Локальная установка 0.4.0: [construction_analytics/README.md](construction_analytics/README.md). Этот файл предназначен агенту внешнего бэка и разработчику аналитических сервисов. JSON Schema находится в [contracts/frame-analysis-v1.schema.json](contracts/frame-analysis-v1.schema.json). Описание семантики ниже обязательно вместе со схемой.

Порядок работы: согласовать этот контракт → настроить существующую аналитику и HTTP → подготовить Docker-поставку → встроить интеграционный модуль во внешний бэк. Аналитика, HTTP и PostgreSQL-справочники реализованы; совместимость с реальным внешним бэком и качество на его данных ещё не проверены.

Корень JSON Schema принимает пять видов сообщений: request, result, error, catalog, capabilities. Для конкретного сообщения можно выбрать одноимённый `$defs`, сохранив остальные определения для разрешения ссылок. Валидатор использует Draft 2020-12 с включённой проверкой `format: date-time`; одних regex недостаточно для проверки календарной даты. Сервисы дополнительно проверяют порядок дат, bbox, уникальные ID, ссылки, каталог, происхождение и реальные байты изображения.

## 1. Граница ответственности

- Внешний бэк владеет площадками, камерами и календарным планом. Он отправляет фотографии, фактический CV, снимок плана и историю наблюдений. Аналитические сервисы не читают его внутренние таблицы, не управляют камерами и не изменяют исходный план.
- Наши два сервиса: `deterministic` (матрица v2, история и правила плана) и `vlm_llm` (изображение → VLM → LLM → группы работ). Каждый развёртывается отдельно. Адреса передаются конфигурацией; имена контейнеров не входят в данные площадки.
- Интеграционный модуль будущего внешнего бэка преобразует его сущности в этот контракт, вызывает оба сервиса, сопоставляет контекст ответов и сохраняет ответы с их происхождением. Язык этого модуля будет выбран после получения стека внешнего бэка.
- PostgreSQL аналитической части содержит справочники и необходимые локальные снимки/артефакты. Копия внешнего плана остаётся копией с исходным ID и версией. Анализ использует переданный снимок истории, а не произвольное объединение всех когда-либо загруженных данных площадки.
- Самостоятельный третий бэк подсистемы из предыдущей версии `SYSTEM_PRD.md` не является условием этой интеграции. Реализация внешнего бэка и отдельного оркестратора отложена.

**Подтверждено пользователем:** фотографии отправляет внешний бэк; он же владеет планом. **Рабочее решение первой версии:** история передаётся явным снимком в каждом запросе. Наличие фактических статусов работ снаружи пока не подтверждено; пустой список подтверждённых событий допустим.

## 2. Единица анализа, идентификаторы и время

Один запрос — один кадр одной камеры одной площадки, один участок плана и одна версия плана. Внешний бэк может обслуживать любое число площадок и камер, разбивая их на такие запросы. Несколько операций внутри кадра могут возвращаться отдельными группами. Несколько кандидатов одной группы означают альтернативы одной операции.

Все внешние ID — непрозрачные строки длиной 1–100 символов: не переводить их в целые числа, не менять регистр, не обрезать и не придумывать вместо отсутствующих. Пробельные ID и начальные/конечные пробелы запрещены. `stage_id` — целое число из нашего версионированного каталога, а не внешний ID работы.

| Идентификатор | Область уникальности / смысл |
| --- | --- |
| `site_id` | Площадка у отправителя. Первую поставку обслуживает один интегрирующий внешний бэк; несколько независимых отправителей потребуют namespace и новой настройки. |
| `camera_id` | Камера внутри площадки. |
| `image_id` | Кадр внутри пары `(site_id, camera_id)`; повторная доставка сохраняет ID. |
| `detection_id` | CV-объект внутри кадра; разные машины одного класса имеют разные ID. |
| `plan_stream_code` | Устойчивый участок с упорядоченной цепочкой плана внутри площадки. Параллельные независимые цепочки используют разные коды. |
| `plan_id`, `revision_id` | Исходный план и его неизменяемая версия у внешнего бэка. |
| `step_key` | Устойчивый пункт внутри участка: при замене вида работы новым `stage_id` нужен новый ключ. Одинаковый `stage_id` разрешён у нескольких пунктов. |
| `snapshot_id` | Неизменяемый снимок истории внутри площадки и участка. Изменение состава истории создаёт новый ID. |
| `request_id` | ID одной попытки логического анализа. Одинаковый для вызовов двух сервисов; повтор запроса сохраняет его. |
| `analysis_id` | ID результата конкретного сервиса, выдаваемый сервисом. |

`observed_at`, сроки плана и времена событий — RFC 3339 с явным поясом, например `2026-09-26T12:00:00+03:00` или `2026-09-26T09:00:00Z`. Для расчётов сравниваются моменты времени, а не строки. `history.as_of` равен моменту `frame.observed_at`: это граница оценки. Наблюдения и подтверждения из будущего не участвуют. Даты плана могут быть будущими.

### Участки и ракурсы

`scope.plan_stream_code` передаёт внешний бэк. `scope.source_ref` фиксирует происхождение привязки камеры/области к участку. `scope.roi_bbox` — область анализа в координатах полного переданного кадра; `null` означает весь кадр, а не неизвестный масштаб.

Если участок неизвестен, все три поля `scope` равны `null`, `plan=null`; ответ содержит `scope_unknown` и не назначает пункт плана. Внешний бэк не подставляет весь объект как участок без основания. Если кадр охватывает несколько известных участков, создаются отдельные запросы с разными ROI и `request_id`; исходные ID кадра сохраняются. Вся история одного запроса относится к выбранному устойчивому участку, даже если камеры разные.

## 3. HTTP и передача фотографии

Оба сервиса предлагают одинаковый маршрут на своих разных базовых адресах:

`POST /v1/analyze/frame`

Запрос: `multipart/form-data`, ровно две части:

| Часть | Тип | Содержание |
| --- | --- | --- |
| `metadata` | `application/json; charset=utf-8` | JSON по `$defs.request` схемы, файловый part с filename, например `metadata.json`. |
| `image` | `image/jpeg`, `image/png` или `image/webp` | Байты единственного кадра. |

Фото передаёт внешний бэк. URL фотографий, пути к локальным файлам и Base64 внутри JSON в v1 не используются. Имя файла в multipart не задаёт идентичность кадра и не используется как путь хранения.

`frame.image_sha256` — SHA-256 **точных отправленных байтов**, 64 строчных hex-символа. Хеш вычисляется после всех преобразований изображения. Декодированные размеры должны совпадать с `width` и `height`, тип — с `media_type` и multipart. Повреждённое изображение отклоняется до вызова модели. Разрешён только один статичный кадр; анимированные/многокадровые файлы отклоняются. Внешний бэк заранее применяет ориентацию EXIF и выдаёт bbox в системе координат этих же пикселей.

Исходные лимиты v1: изображение до 25 000 000 байт, metadata до 1 000 000 UTF-8 байт, стороны изображения до 8192 пикселей, до 40 000 000 пикселей суммарно. До 200 детекций на кадр, 500 шагов плана, 500 исторических кадров и 1000 подтверждённых событий. Превышение возвращает `413`; незаметное обрезание запрещено. Подготовленный модельный контекст также имеет лимит, публикуемый сервисом; превышение возвращает `context_too_large`, а не удаление последних пунктов плана.

Заголовки:

- `Idempotency-Key`: точно `request_id` из metadata.
- `Authorization: Bearer <service-token>`: общий для этой интеграции сервисный credential; конкретное значение задаётся при развёртывании. Это не ключ gateway моделей.
- `Accept: application/json`.

Сервис возвращает `application/json; charset=utf-8`. Успешно выполненный анализ — `200`, включая недостаток признаков, неизвестный участок и отсутствие плана. Ошибка выполнения — отдельный неуспешный HTTP-ответ, без вымышленного аналитического результата.

## 4. Входной JSON

`schema_version = frame-analysis-input-v1`. Все перечисленные поля обязательны. Если допускается отсутствие значения, передаётся `null`; отсутствие ключа не равно `null`. Дополнительные поля запрещены, чтобы ошибки написания не исчезали молча.

| Поле | Формат / смысл |
| --- | --- |
| `request_id`, `site_id` | ID из раздела 2. |
| `object_type_code` | `null` либо `housing`, `education`, `healthcare`, `sports`, `culture`, `administrative`, `preschool`, `office`, `roads`. Неизвестный тип — `null`. |
| `catalog_version` | Версия нашего каталога, по которой сопоставлены `stage_id` и канонические CV-классы. |
| `frame` | Поля `image_id`, `camera_id`, `observed_at`, `source_ref`, `image_sha256`, `media_type`, `width`, `height`. `source_ref` — проверяемая ссылка/ID источника, не команда загрузить URL. |
| `scope` | `plan_stream_code`, `roi_bbox`, `source_ref`; правила раздела 2. |
| `cv` | Состояние внешнего CV и отдельные детекции; раздел 5. |
| `plan` | `null` либо полный снимок шагов выбранного участка; раздел 6. |
| `history` | Явный снимок истории; раздел 7. |

Детерминированный сервис использует только фактический внешний CV для матрицы и временных сигналов. Он принимает кадр для единого контракта и проверки идентичности, но не извлекает из него новые модельные признаки. VLM → LLM использует тот же кадр и контекст; весь проверенный ответ VLM передаётся LLM, как в существующем CLI.

## 5. CV и координаты

`cv` содержит `status`, `source_ref`, `model_version`, `detections`.

- `status=ok`: источник известен, `source_ref` непустой. Пустой массив означает, что CV успешно отработал и не вернул объектов.
- `status=unavailable` или `failed`: `detections=[]`; `source_ref` допускает `null`. Отсутствующий CV нельзя представлять успешным пустым результатом. VLM-анализ может продолжаться с ограничением; матрица не получает фиктивные классы.
- `model_version`: точный ID модели/версии внешнего CV либо `null`, если источник его не предоставляет.

Каждая детекция имеет поля:

| Поле | Формат |
| --- | --- |
| `detection_id` | Неповторяющийся внутри кадра ID. |
| `class_code` | Канонический класс **техники** из каталога. Внешние `excavator`, `Excavator` и другие названия преобразуются по явной таблице соответствия; неизвестное соответствие даёт `422 unknown_class`, а не ближайший класс. |
| `bbox` | Четыре числа `[x_min, y_min, x_max, y_max]`, каждое в `[0,1]`. |
| `confidence` | Число в `[0,1]` либо `null`, исключительно оценка фактического детектора. |

Начало координат — левый верхний угол; x вправо, y вниз. Обязательны `x_min < x_max`, `y_min < y_max`. Нормализация: x делится на ширину, y на высоту **переданного полного кадра**. Форматы `xywh`, пиксели и координаты другого resize требуют преобразования внешним адаптером до отправки.

Если задан ROI, внешний бэк отправляет CV только относящейся к этому участку области. Сервис проверяет нахождение центров bbox внутри ROI. Детекция, пересекающая несколько участков, не назначается обоим как два независимых свидетельства: ответственность за явное распределение принадлежит адаптеру, неоднозначность сохраняется в ограничениях.

`count` и `moving` во входе v1 отсутствуют. Количество вычисляется по отдельным детекциям; движение нельзя придумывать по одному фото. Суммирование одинаковых классов не повышает число независимых технологических признаков.

## 6. План, которым владеет внешний бэк

`plan` содержит `plan_id`, `revision_id`, `source_ref`, `steps`. Версия опубликована/зафиксирована источником и неизменяема. Ключ локального снимка — `(site_id, plan_stream_code, plan_id, revision_id)`: разные участки одной внешней версии имеют разные снимки. Повтор с тем же ключом и изменённым содержимым — конфликт контекста, а не обновление на месте.

`steps` — **полная упорядоченная цепочка выбранного участка**, а не top-N кандидатов по CV. В v1 принимаются concrete и no_class; summary отклоняется. Вид определяется каталогом по stage_id, дополнительное поле запроса не требуется. Невизуальные работы не удаляются из цепочки и аудита. Параллельные цепочки представлены разными участками. Пустой план передаётся как `plan=null`, а не как `steps=[]`.

Шаг содержит `step_key`, `sequence_no` (положительное целое), `stage_id`, `planned_start_at`, `planned_end_at`. Ключи и sequence уникальны в снимке; конец строго позже начала; начала не убывают по sequence. Последовательность не обязана иметь непрерывные номера, а плановые интервалы могут перекрываться. `stage_id` существует в заявленной версии каталога, обозначает concrete или no_class и применим к известному типу объекта. Отсутствие progress у допустимой работы не является ошибкой входа.

Агент внешнего бэка должен сделать явное соответствие его пунктов нашему каталогу, сохраняя исходный ключ в `step_key`. Не сопоставлять работы автоматически только по похожему названию. Если конкретный пункт нельзя сопоставить, целостный плановый анализ этого участка пропускается с `plan=null`; адаптер сохраняет причину у себя. Нельзя удалить неизвестный промежуточный пункт и выдать следующий известный за «непосредственно следующий».

Смена версии в ходе запроса не меняет отправленный снимок. Новый анализ получает новую версию и новый `request_id`. Старый результат хранится как оценка старой версии, а не переписывается.

## 7. История и подтверждённый ход

`history` содержит `snapshot_id`, `as_of`, `window_start`, `complete`, `observations`, `progress_events`. `window_start <= as_of`; `as_of` равен времени текущего кадра. `complete=true` означает, что источник передал все относящиеся к участку записи доступного ему окна, включая признаки качества CV; это не утверждение, что камеры непрерывно видели площадку. При потерях/обрезке ставится `false`.

### Историческое наблюдение

Поля: `observation_id`, `image_id`, `camera_id`, `observed_at`, `source_ref`, `image_sha256`, `cv`. Времена лежат в `[window_start, as_of]`. CV имеет ту же структуру, что у текущего кадра. Для временного анализа исторические изображения не передаются; ссылки и хеши позволяют проверить происхождение. Все записи относятся к `site_id` и `plan_stream_code` текущего запроса; их bbox нормализованы по своим исходным кадрам.

Текущий кадр в `observations` не дублируется. Уникальность наблюдения определяется `(site_id, camera_id, image_id)`, а не случайным новым `observation_id`. Повтор с тем же ID и другим хешем/временем — `409 observation_identity_conflict`. Дубли удаляются источником; сервис проверяет это дополнительно. Несколько камер одного участка в один момент объединяются в одну временную точку подтверждения, а не в несколько разнесённых наблюдений.

### Подтверждённое событие

Поля: `event_id`, `step_key`, `stage_id`, `plan_revision_id`, `state`, `effective_at`, `recorded_at`, `source_ref`, `actual_started_at`, `actual_completed_at`.

- `state`: `not_started`, `in_progress`, `completed`. Неизвестное состояние представляется отсутствием события.
- `effective_at`: время, на которое источник утверждает состояние; `recorded_at`: время регистрации этим источником. Оба не позже `as_of`; источник обязателен.
- `actual_started_at`, `actual_completed_at`: достоверные моменты начала/окончания либо `null`. `recorded_at` и время получения ответа не подменяют фактическое начало/окончание. Завершённое состояние без точного `actual_completed_at` допустимо.
- `actual_completed_at` допускается только при `completed`; фактические времена не позже `effective_at`, а завершение не раньше известного начала. При `not_started` оба фактических времени равны `null`.
- События ссылаются на шаг текущего снимка. Событие прежней версии разрешено лишь при неизменных `step_key` и `stage_id`; внешний бэк подтверждает это соответствие. Удалённые из текущего плана пункты не используются как якорь.
- История append-only: исправление — новое событие. Последнее состояние выбирается по `(effective_at, recorded_at)`; разные состояния одного шага с одинаковой парой времени — `422 ambiguous_progress`, а не произвольный порядок по ID.

`progress_events` могут предшествовать `window_start`: окно ограничивает CV-наблюдения, но не удаляет необходимую подтверждённую позицию плана. Отсутствие событий разрешено и возвращает `needs_progress_anchor`; модельные гипотезы не добавляются в этот массив автоматически.

## 8. Успешный ответ

`schema_version = frame-analysis-result-v1`. Общие поля обоих сервисов:

| Поле | Формат / смысл |
| --- | --- |
| `request_id`, `analysis_id` | Корреляция запроса и результата. |
| `service` | `deterministic` или `vlm_llm`. |
| `context` | `site_id`, `camera_id`, `image_id`, `observed_at`, `image_sha256`, `plan_id`, `plan_revision_id`, `plan_stream_code`, `history_snapshot_id`, `catalog_version`, `input_sha256`. Отсутствующие план/участок — `null`. |
| `versions` | `service_version`, `matrix_version`, `profiles_version`, `vision_model`, `llm_model`, `schedule_rules_version`. Неприменимые значения — `null`. |
| `current_work` | `status` и `work_groups`. |
| `visual_observations`, `visual_relations` | Реестры визуальных свидетельств ответа; для deterministic пустые. |
| `transition` | Отдельная оценка следующей работы; раздел 9. |
| `schedule` | Отдельная оценка срока; раздел 10. |
| `limitations` | Массив конкретных ограничений, максимум 20 строк по 1000 символов. |

`current_work.status`: `assessed` (есть группы), `insufficient_evidence` (нет достаточных признаков), `outside_plan` (наблюдаемые признаки не совместимы с переданным планом), `no_plan`, `scope_unknown`. Во всех исходах кроме `assessed` группы пустые. При неизвестном участке приоритет имеет `scope_unknown`; при известном участке и отсутствующем плане — `no_plan`. Ошибка модели не является `insufficient_evidence`.

### Рабочая группа

До восьми групп в ответе. Поля группы:

- `group_id`: ID внутри результата.
- `match_status`: `specific` при одном кандидате, `ambiguous` при 2–10 альтернативах.
- `candidates`: массив `{step_key, stage_id, ranking}`. Ключ и ID должны соответствовать **одному и тому же** шагу переданного плана; `ranking=null` для VLM → LLM.
- `visual_state`: `operation_indicated`, `presence_or_result_only` либо `not_evaluated` для deterministic. Это не подтверждение выполнения.
- `area_bbox`: нормализованный bbox группы или `null`, если надёжной локализации нет. Для deterministic это область применения результата, а не область новой визуально обнаруженной операции.
- `evidence`: 1–24 свидетельства `{source, ref, role, explanation}`. `source`: `cv_detection`, `visual_observation`, `visual_relation`, `progress_event`; `role`: `supports` либо `contradicts`.
- `explanation`: короткое обоснование, до 1000 символов.

`ref` — JSON Pointer. Для CV и progress он указывает в **metadata запроса**, например `/cv/detections/0`, `/history/observations/0/cv/detections/1`, `/history/progress_events/0`. Для визуальных наблюдений/отношений — в JSON ответа: `/visual_observations/0`, `/visual_relations/0`. Разрешены ссылки только на существующие элементы коллекции соответствующего `source`. Индексы относятся к неизменённому исходному массиву, а не к внутреннему отсортированному списку.

Визуальное наблюдение: `{id, description, certainty, bbox}`; certainty — `low`, `medium`, `high`. Визуальное отношение: `{id, subject_id, predicate, object_id, certainty, description}`; subject/object ссылаются на ID наблюдений; predicate — `inside`, `on`, `adjacent_to`. Внутренний полный VLM-record сохраняется для аудита отдельно; эти реестры дают потребителю основания групп.

Каждая VLM-группа имеет собственное поддерживающее визуальное наблюдение средней/высокой certainty. Одно наблюдение нельзя размножить в несколько операций без отличительных опор. Проверка ID и bbox не доказывает семантическую независимость: это ограничение сохраняется. Группа в ROI не использует признаки другого участка. Общий список техники кадра автоматически каждой группе не назначается.

### Ранжирование deterministic

`ranking` кандидата: `status` (`context_only`, `single_signal`, `supported_candidate`), `signal_score`, `role_score` (числа 0–10), `matches` — массив `{class_code, role_weight, signal_weight, evidence_group}`. Веса — целые 0–3, `signal_weight <= role_weight`. Условия применимости матрицы учитываются и поясняются в evidence/explanation; простое присутствие класса не доказывает активность.

Ранжируются только конкретные работы переданного плана. Совпадающий каталоговый ID раскрывается в соответствующие отдельные `step_key`, сохраняя неоднозначность. Общий набор CV одного участка образует область совместимости; детерминированные альтернативы не выдаются за локализованные параллельные операции. `signal_score`, `role_score`, SQL coverage и certainty не являются вероятностями и не складываются в общий confidence.

## 9. Следующая работа и временные сигналы

`transition` содержит `status`, `current_step_key`, `next_step_key`, `distinctive_codes`, `evidence_first_at`, `evidence_last_at`, `supporting_observations`, `evidence_refs`.

Статусы: `no_published_plan`, `needs_progress_anchor`, `no_next_stage`, `not_distinguishable_by_equipment`, `no_signal`, `single_or_short_signal`, `possible_start`, `history_incomplete`, `cv_unavailable`, `not_evaluated`. VLM → LLM возвращает `not_evaluated` с пустыми доказательствами и `null` ключами/временами.

Deterministic переносит алгоритм существующего `assess_next_stage` в Python для переданного снимка: проверяется следующий пункт после подтверждённой позиции с обязательной проверкой невизуальных барьеров (раздел 15). Поздний anchor не обходит незавершённый no_class. Сигнал — класс техники следующей работы, отсутствующий в перечне предыдущей concrete-работы. Перечни берутся из положительных equipment-связей **матрицы v2**, а не старой SQL-матрицы. Исходное окно — семь дней; порог — минимум две **разные временные точки** с разницей минимум 15 минут. Камеры одного времени и повтор кадра не увеличивают число точек. `supporting_observations` означает число этих временных точек; это уточнение старого SQL-счётчика ID. Сброс sourced progress в not_started исключает сигналы до нового начала. Старые SQL-функции сохранены отдельно и HTTP их не вызывает.

`possible_start` требует полного снимка нужного окна, отличительных классов и ссылок на реальные детекции. Он сохраняет время первого сигнала и не записывает подтверждённое начало. Окно короче семи дней допустимо, если начинается не позже подтверждённого начала текущей работы/якоря, ограничивающего SQL-окно; иначе `history_incomplete`. `complete=false` также даёт `history_incomplete`, сохраняя текущую оценку совместимости отдельно. Недоступный CV не означает отсутствие техники; частично недоступное покрытие указывается в limitations.

## 10. Предположение об отставании

Эта логика реализована в deterministic как `schedule-rules-v1`. Она отделена от текущих кандидатов и `possible_start`.

`schedule` содержит `status` (`possible_delay`, `no_delay_indicated`, `insufficient_evidence`, `not_evaluated`) и `items`. Элемент: `{step_key, stage_id, status, reason_code, overdue_seconds, evidence_at, evidence_refs}`. У элемента нет `not_evaluated`; отсутствие оценки обозначается пустым массивом на уровне блока. VLM → LLM в v1 возвращает `not_evaluated`; правила срока выполняет deterministic по тому же снимку.

Консервативные правила v1:

| Данные по пункту | status / reason_code |
| --- | --- |
| Подтверждено фактическое окончание позже планового | `possible_delay` / `actual_completion_after_deadline`; overdue = actual_completed_at − planned_end_at. |
| Последнее подтверждённое состояние `not_started` или `in_progress` действует на момент после планового окончания | `possible_delay` / `open_state_after_deadline`; overdue = effective_at − planned_end_at. Это нижняя граница по моменту свидетельства, а не длительность до текущего кадра. |
| Подтверждено фактическое окончание не позже планового | `no_delay_indicated` / `completed_by_deadline`; overdue = 0. |
| Плановое окончание ещё не наступило, других оснований нарушения срока нет | `no_delay_indicated` / `deadline_not_reached`; overdue = 0. Это не прогноз выполнения в срок и не проверка даты начала. |
| Плановое окончание прошло, есть только статус completed без фактического времени окончания | `insufficient_evidence` / `actual_completion_time_unknown`; overdue = null. |
| Плановое окончание прошло, нет подходящего подтверждённого состояния после него | `insufficient_evidence` / `no_sourced_progress`; overdue = null. |

Состояние `in_progress` до дедлайна само по себе не доказывает задержку после дедлайна. Отсутствие машины, `no_signal`, отсутствие нового подтверждения и одиночный снимок не создают `possible_delay`. Для rules v1 нарушение плановой даты начала отдельно не оценивается. `evidence_at` — момент источника, поддерживающего вывод; для ещё не наступившего дедлайна это `as_of`. Блок без плана/участка — `insufficient_evidence`, `items=[]`.

Общий статус: если есть хотя бы один `possible_delay`, он сохраняется; иначе при хотя бы одном `insufficient_evidence` — `insufficient_evidence`; иначе при непустом наборе проверенных пунктов — `no_delay_indicated`. Одновременный известный риск одного пункта и неизвестность других раскрываются в items и limitations.

Более сильные выводы по последовательностям изображений и длительности этапов потребуют отдельной проверенной версии правил; они не имитируются в v1.

Сервис проверяет recorded_at ≥ effective_at и фактические времена ≤ effective_at. Противоречащие состояния одного пункта с одинаковыми effective_at/recorded_at отклоняются как ambiguous_progress.

## 11. Ошибки, повторы и идентичность контекста

Ошибка имеет `schema_version=frame-analysis-error-v1`, `request_id` (null, если разобрать ID нельзя), `service`, `code`, `message`, `details`, `retryable`, `execution_state`. `details` — массив `{path, code, message}`, path — JSON Pointer к полю либо пустая строка для всего запроса. `execution_state`: `not_started`, `failed`, `unknown`.

| HTTP | code | Поведение клиента |
| --- | --- | --- |
| 400 | `invalid_request` | Исправить JSON/multipart/заголовки. |
| 404 | `analysis_not_found` | В долговечном журнале этого сервиса ещё нет запроса для указанной площадки. |
| 401 / 403 | `unauthorized` / `forbidden` | Исправить доступ. |
| 409 | `idempotency_conflict`, `observation_identity_conflict`, `plan_identity_conflict`, `catalog_version_mismatch`, `execution_uncertain` | Разобрать конфликт или неопределённое выполнение; не менять ID ради обхода проверки. |
| 413 | `payload_too_large`, `context_too_large` | Исправить объём/границы анализа явно. |
| 415 | `unsupported_media_type` | Передать поддерживаемый тип. |
| 422 | `invalid_context`, `invalid_image`, `image_hash_mismatch`, `unknown_class`, `unknown_stage`, `ambiguous_progress` | Исправить данные/соответствие. |
| 429 | `busy` | Retry-After; повтор тех же данных и ID, если retryable=true. |
| 502 | `model_invalid_response`, `model_failure` | Сохранить техническую ошибку, не заменять её недостатком признаков. |
| 503 | `not_ready`, `dependency_unavailable` | Ограниченный повтор, если retryable=true. |
| 504 | `analysis_timeout` | Повтор только при известном состоянии и retryable=true. |
| 500 | `internal_error` | Сохранить ошибку и request_id; автоматический повтор не предполагается. |

Секреты, Authorization, исходные тела транспортных исключений и stack traces в ответ не попадают. `message` человекочитаемое; логика клиента опирается на `code`, а не на его текст.

Fingerprint запроса `input_sha256`: SHA-256 от `UTF8(metadata как отправлено) + один байт 0x00 + байты image`. Multipart boundary и имя файла не входят. Адаптер сохраняет сериализованные байты metadata для повтора: изменение порядка ключей тоже меняет fingerprint. Оба сервиса получают одинаковые metadata и кадр и возвращают одинаковый input_sha256.

Ключ идемпотентности имеет область `(service, site_id, request_id)`. Тот же ключ с другим fingerprint даёт `409`. Тот же ключ и вход после успешного анализа возвращают сохранённый результат с прежним analysis_id. Одновременный повтор уже выполняющегося запроса даёт `429 busy` с Retry-After. Будущая реализация обязана хранить журнал запросов вне записываемого слоя контейнера; отдельные вызовы двух разных сервисов являются разными анализами.

Если ответ gateway потерян и неизвестно, выполнен ли платный вызов, возвращается `execution_state=unknown`, `retryable=false`; повтор не запускает его заново автоматически. Потеря HTTP-ответа клиенту требует проверки результата по `GET /v1/analyses/by-request/{request_id}?site_id=<URL-encoded-id>` у соответствующего сервиса. Этот маршрут возвращает сохранённый ответ 200, busy 429, неизвестное выполнение 409 `execution_uncertain` или 404 `analysis_not_found`. Эти два кода также входят в error schema. Неизвестный запрос после потери соединения не является доказательством отсутствия затрат gateway.

Начальная политика клиента: максимум два повтора после исходного вызова, задержки 1 и 2 секунды либо больший Retry-After. Автоматически повторяются только явно retryable busy/not_ready/dependency_unavailable. Повторы невалидного ответа модели выполняет сам сервис (до одного повтора каждого модельного шага), а не внешний адаптер. Общий HTTP timeout первой поставки — 1020 секунд: текущие четыре предельных модельных попытки по 240 секунд оставляют запас. Это исходный предел совместимости, не заявленная задержка; реальные p95 и допустимый SLA требуют измерения. Отмена клиента не доказывает отмену обработки.

## 12. Согласование двух ответов во внешнем модуле

Сервисы вызываются независимо с тем же request_id и fingerprint. Ошибка одного не уничтожает валидный ответ другого. Перед сравнением проверяются все поля context, включая кадр, версию плана, участок и snapshot истории. Несовпадение — технический конфликт, а не согласие.

Модуль сохраняет исходные ответы обоих сервисов. Совпадение кандидатов позволяет показать совместимую гипотезу; оно не подтверждает ход работ и не отменяет альтернативы. Содержательное расхождение сохраняется для проверки. Пороговые правила автоматического выбора одного победителя в v1 отсутствуют. Единственный stage_id выдавать нельзя, если есть несколько групп или неоднозначная группа. Ошибка сервиса, недостаток признаков и outside_plan отображаются раздельно.

`transition` и `schedule` присоединяются по `step_key` и участку и остаются отдельными от визуального предположения. Численные вероятности и автоматические обновления confirmed progress не создаются.

## 15. Невизуальные пункты в релизе 0.2.0

no_class (например 39 «Закупка оборудования») принимается в полном плане, но не включается в deterministic-кандидаты или модельные группы. Для модели передаются полный план и подтверждения, а разрешённые step_keys ограничены concrete одновременно схемой и валидатором. Некорректный выбор проходит один форматный повтор, затем даёт model_invalid_response.

План только из no_class возвращает current_work=insufficient_evidence без gateway-вызова и без ключа; у VLM transition/schedule остаются not_evaluated. Readiness VLM без ключа по-прежнему 503. Поля vision_model/llm_model обозначают настроенную модель и сохраняются по схеме v1 даже в пропущенной ветке; факт пропуска указан в limitations, модельных попыток в журнале нет.

В цепочке concrete A → no_class B → concrete C последовательный переход блокируется, пока latest sourced progress B не равен completed. Возвращаются not_distinguishable_by_equipment, next_step_key=B и явное ограничение. Более позднее подтверждение C не обходит B. Для нескольких no_class нужно завершение каждого; более новое not_started/in_progress отзывает завершение. После подтверждения B наблюдения до actual_completed_at (либо effective_at без фактического времени) не засчитываются. Самостоятельные визуальные гипотезы о C остаются допустимы, но не подтверждают B.

Сроки no_class оценивает только deterministic по прежним schedule-rules-v1: позднее фактическое завершение или sourced незавершённость после дедлайна дают possible_delay; нет источника/источник до дедлайна — insufficient_evidence. Отсутствие техники не доказывает отставание.

## 14. Отличия от текущего CLI и необходимые проверки

Совместимый CLI принимает `llm-stage-input-v1` и отдаёт `llm-stage-assessment-v2`; напрямую новый контракт он не читает. CLI и HTTP используют общее ядро `construction_analytics.pipeline`; новый HTTP-адаптер выполняет явное преобразование:

| HTTP-контракт | Реализованное преобразование / совместимость CLI |
| --- | --- |
| site_id, scope.plan_stream_code, plan.revision_id | site_ref, plan_stream_code, plan_revision_ref. |
| frame.image_id, observed_at, image_sha256 и image-part | image_id, observed_at, image_sha256 и --image. |
| cv.detections | HTTP передаёт отдельные detection_id/bbox модели и проверяет связь с областью группы; legacy CLI сохраняет агрегированный equipment. |
| plan.steps | Нынешний plan_steps; optional sourced progress собирается из history.progress_events. |
| Отдельные CV-ссылки и реестры визуальных опор | HTTP преобразует модельные ID детекций/событий/наблюдений в JSON Pointer и проверяет ссылки; CLI сохраняет старые CV-коды и VLM ID. |
| history, transition, schedule | CLI не проверяет временной переход и задержку. HTTP deterministic выполняет transition с дедупликацией и schedule-rules-v1. |
| Версии, аудит и идемпотентность | HTTP использует PostgreSQL-справочники и долговечный журнал с оригинальными metadata/image и попытками; CLI сохраняет файловые артефакты и хеш SQLite. |

Перед готовностью интеграции проверяются: два сервиса на одном реальном входе; hash/MIME/размеры; bbox и ROI; неизвестные классы и каталоговые ID; повтор доставки; два одновременных ракурса; пустой/недоступный CV; неизвестный участок; отсутствующий план/прогресс; альтернативы и две независимо видимые работы; старые версии; неполная история; смена плана; модельная ошибка; неопределённость gateway; сохранение результата при пересоздании контейнеров; источники и времена каждого сигнала срока. Проверка JSON Schema проверяет структуру, а не выполнение этой логики.

## 16. Необязательная оценка активности техники (0.4.0)

Оба `/v1/analyze/frame` принимают дополнительный корневой объект `equipment_activity` (`$defs.activityOptions`). При включении обязательны `schema_version="equipment-activity-options-v1"`, `camera_stable` и `idle_candidate_classes` с каноническими кодами. Рабочий период задаётся `working_period={start_at,end_at,source_ref}`; даты должны определять положительный интервал, текущий кадр для idle должен попадать в него. Без периода или разрешения класса оценка остаётся `stationary_observed`/`unknown`. Настройки, значения по умолчанию и пример: [construction_analytics/README.md](construction_analytics/README.md#движение-и-возможный-простой-техники). Параметры — часть неизменяемого запроса, не настройки env.

В `cv.detections` текущего и исторических кадров можно передать nullable `track_id`, постоянный для физической машины внутри одной камеры. Он уникален в кадре и сопоставляется вместе с классом. Иначе используется взаимно однозначная геометрическая ассоциация. Передавать track_id только в одном конце пары нельзя: это разрывает идентичность. Источник отвечает за устойчивость tracking ID и ракурса; сервис не делает стабилизацию камеры. При расширении несколько наблюдений одной камеры в одинаковое время отклоняются. Наблюдения других камер не участвуют в оценке машины.

История обязана содержать фактические bbox/confidence и время каждого кадра; `history.complete=false` запрещает `possible_idle`. По умолчанию порог 14400 с, максимальный интервал 1800 с, confidence ≥0.5. Разрыв сопоставления, отсутствие detection, недоступный CV или слишком большой интервал обрывает цепочку; одна пара кадров с разницей четыре часа недостаточна. Каждый bbox сравнивается с текущим, поэтому накопленное движение учитывается. Список разрешённых классов определяется политикой площадки, не выводится автоматически из матрицы работ. `class_idle_threshold_seconds` переопределяет общий порог для выбранных классов.

Ответ добавляет `equipment_activity` (`$defs.activityResult`) с параметрами, версией правил и текущими машинами. Статусы: `movement_indicated`, `stationary_observed`, `possible_idle`, `operation_indicated`, `unknown`. JSON Pointer в `evidence_refs` указывает на конкретную текущую/историческую detection входного metadata; `visual_activity_refs` указывает на группу итогового ответа. `stationary_observation_span_seconds` описывает промежуток между подтверждающими неподвижность снимками. `last_change_at` обозначает более новый снимок на границе изменения, а не физическое время движения. Внешний интерфейс должен отображать `possible_idle` как подозрение, учитывать `reason_codes` и `limitations`; время между снимками и работа на месте не наблюдаются. Прямые supports-ссылки текущей VLM-группы с operation_indicated блокируют подозрение, но не подтверждают работу каждого участника. Исторические изображения/VLM-оценки не проверяются.

`versions.equipment_activity_rules_version="bbox-equipment-activity-v1"` сохраняется вместе с результатом. Миграция БД не требуется. Без поля расширения ответ имеет прежнюю форму; поддержка обнаруживается через авторизованный `GET /v1/capabilities?include_extensions=true`, который добавляет `extensions=["equipment-activity-v1"]`. Обычный capabilities не меняет набор полей. Старые клиенты могут продолжать отправлять v1; клиенты расширения должны использовать обновлённую схему. Повторные запросы/lookup возвращают сохранённую оценку, а изменение metadata при прежнем Idempotency-Key даёт 409. Архивные образы 0.2.0 это расширение не реализуют; необходим пакет/сборка 0.4.0. Точность на реальном источнике пока требует отдельной проверки.

## 17. Качественные сигналы хода работ (0.4.0)

Включение equipment_activity также включает новый необязательный объект результата `work_progress` (`$defs.workProgress`) и `versions.work_progress_rules_version="equipment-work-progress-v1"`. Настройки входа прежние. Клиенту расширения необходима текущая JSON Schema и пакет сервиса 0.4.0; обычные запросы без расширения сохраняют прежний результат. Сохранённые оценки 0.3.0 возвращаются без пересчёта: для нового анализа нужен новый request_id и, при изменении истории, новый snapshot_id.

`work_progress.steps` содержит каждый пункт плана в порядке sequence_no, сохраняя step_key повторений. `confirmed_state`, `confirmed_at`, `progress_evidence_refs` берутся из последнего sourced progress. `activity_status` — отдельный качественный сигнал: operation_indicated, equipment_movement_indicated, possible_inactivity, presence_only, insufficient_evidence, not_visual. `candidate_match_status` отражает specific/ambiguous/compatibility_only/not_selected; один класс или сигнал не определяет точную работу и не доказывает несколько параллельных операций. summary поясняет число переданных подтверждений и качественных кандидатов, не выполненный объём. `confirmed_completed_steps`/`total_plan_steps` — счётчики пунктов, не процент готовности объекта.

Машины с possible_idle не входят в положительные признаки активности. deterministic исключает конкретные current/history detections неподвижной цепочки из ранжирования и transition, сохраняя другие машины того же класса, другие камеры и более ранние свидетельства. stationary_observed/unknown сохраняют контекст присутствия, не подтверждая остановку. VLM получает предварительную оценку как дополнительный контекст; прямые признаки текущей операции могут её опровергнуть. Для выбранной VLM-группы summary относит к работе только её прямые CV supports. Кандидаты по присутствию/результату могут сохраняться в current_work; активность читается совместно с work_progress и visual_state.

`supporting_detection_refs`, `ignored_idle_detection_refs`, `uncertain_detection_refs` указывают на detections входного metadata. `progress_evidence_refs` указывает на sourced progress там же; `activity_evidence_refs` и `visual_activity_refs` — на объекты результата. Корневой excluded_detection_refs содержит весь исключённый idle-интервал, включая историю. next_stage_status повторяет transition.status; у VLM not_evaluated. Простои не подтверждают отставание, движение не выставляет in_progress/completed. schedule сохраняет прежние правила по внешнему ходу и датам. Новая активность у завершённого пункта даёт activity_after_sourced_completion для проверки; подтверждённый источник не меняется. Без плана/привязки участка steps=[] и соответствующий status; пункты no_class остаются внешними подтверждениями. Описание: [construction_analytics/README.md](construction_analytics/README.md#как-активность-помогает-оценить-ход-работ).

## 18. Что ещё требует подтверждения

1. Реальный пример данных и стек внешнего бэка: контракт — проект нашей стороны, его поддержка другой командой ещё не подтверждена.
2. Сопоставление внешних пунктов плана с каталогом и камер/ROI с устойчивыми участками.
3. Доступность и источник confirmed progress, точных actual_started_at/actual_completed_at. При их отсутствии допустим недостаток данных по сроку.
4. Число камер, частота, размеры окон, бюджет, допустимое время ответа. Превышение исходных лимитов потребует нового согласования, не молчаливого обрезания.
5. Deployment-адреса, секрет подключения, права на артефакты и срок долговечного аудита. HTTP-идемпотентность не заменяет хранение истории.

Агент внешнего бэка не должен создавать fake CV, фиктивный план, несourced progress или автоматически подтверждать работу по ответу модели. Если обязательный контекст отсутствует, используется предусмотренный исход/ошибка, а отсутствие доступа фиксируется явно.
