# СтройКонтроль — интерфейс

Веб-интерфейс сервиса мониторинга строительных площадок по видео с камер (ЛЦТ 2026, команда «Работяги»).
Все данные приходят с бэкенда ([../backend](../backend/README.md)); в самом интерфейсе остались только подписи и цвета.

## Запуск

Сначала запустите бэкенд (порт 8100) и шлюз видео (`bash ../tools/video-gateway.sh`), затем:

```bash
npm install
npm run dev        # http://localhost:5180 — запросы /api и /media проксируются на http://localhost:8100
npm run build      # сборка в dist/
npm test           # тесты (Vitest): отставание в днях, разбор адреса камеры, советы по ролям, статус плитки видео
npm run test:e2e   # смоук по ролям (Playwright): сам поднимает бэкенд (:8102, временная база), имитацию сервисов аналитики (:8302) и интерфейс (:5191)
npm run gen:api    # типы из схемы API бэкенда → src/api/openapi.d.ts; src/api/contract.ts сверяет с ними data/types.ts при сборке
```

Для `test:e2e` один раз нужен браузер: `npx playwright install chromium` (или `PW_CHANNEL=chrome npm run test:e2e` —
в установленном Google Chrome). Тесты входят каждой ролью, открывают её экраны и проверяют действия без ошибок
в консоли браузера; прораб — ещё и на экране телефона.

Другой адрес бэкенда для dev-сервера: `VITE_BACKEND_URL=http://host:8100 npm run dev`.
Если интерфейс и API живут на разных доменах — соберите с `VITE_API_URL=https://api.example.ru/api`.
Адрес шлюза видео отдельно задавать не нужно: интерфейс берёт его из `/api/meta` (настройка сервера `SK_VIDEO_WEBRTC_URL`).
На публичном HTTPS с тем же origin видео автоматически идёт через `/hls/` same-origin nginx-прокси; локальная установка
сохраняет WebRTC/WHEP.

## Роли

Экран входа: логин и пароль. Новая установка не содержит демонстрационных учётных записей.
Если на сервере включён Keycloak (см. [backend/README](../backend/README.md#вход-через-keycloak-необязательно)), вместо формы —
кнопка «Войти через Keycloak»; режим интерфейс узнаёт из `/api/meta` сам.
Права проверяет сервер, интерфейс только прячет лишнее.

| Роль | Разделы | Что может |
|---|---|---|
| **Прораб** | Сегодня · Камеры · План — только свой объект | Ответить на предупреждение: «Техника едет», «Подтверждаю проблему», «Это ошибка», «Устранено». План и выполнение видит, но не отмечает |
| **Руководитель проекта** | Объекты · Камеры · Отклонения · Отчёты | Подтвердить / закрыть отклонение, загрузить фото для анализа сервисами по плану объекта, задать подключение Spider для объекта и включить его для нужных камер, настроить план и зоны, отметить выполнение работ, отправить кадры сервисам аналитики вне расписания |
| **Инспектор** | Нарушения · Камеры · Отчёты | Выдать предписание, закрыть нарушение, выгрузить CSV |
| **Администратор** | Объекты · Камеры · Отклонения · Отчёты · Управление | Всё, что остальные роли. Объекты добавляет в их списке, меняет план, зоны и удаляет — на странице объекта; камеры добавляет, меняет и удаляет в разделе «Камеры». В «Управлении» — сотрудники и пароли, правила «этап → техника», журнал действий |


## Видео с камер

- **Видеостена** (раздел «Камеры» и вкладка «Камеры» объекта): все камеры сразу показывают живое видео через шлюз
  MediaMTX. На локальной установке это WebRTC с задержкой около полусекунды; публичный HTTPS использует HLS, потому
  что ingress не открывает UDP для WebRTC. Браузер не умеет RTSP, поэтому видео камеры идёт через шлюз, а не напрямую.
  HLS-клиент обновляет Keycloak-токен и передаёт `Authorization` на манифесты и сегменты; токен не попадает в URL.
  Nginx дополнительно проверяет Keycloak-токен и доступ к камере на **каждом** HLS-ресурсе: MediaMTX сам по себе не
  требует Bearer при запросе сегментов с уже выданным `session` ID.
  Подключаются только плитки, видимые на экране; когда вкладка браузера скрыта, видео на паузе.
- **Клик по камере — просмотр на всю вкладку** (без полноэкранного режима браузера). Стрелки ← / → переключают
  соседние камеры, Esc — выход.
- **Рамки техники** поверх видео. Модель распознавания на сервере разбирает видео камер, которые открыты на экране
  (5–8 раз в секунду на камеру; внешний сервис разметки, если подключён, — 10–15), рамки приходят по WebSocket
  `/api/tracks` и плавно едут за техникой по номеру трека (`lib/useTracks.ts`, `video/TrackBoxes`). В WebRTC видео
  придерживается на ~150 мс, чтобы рамка попадала в машину; у HLS задержка зависит от сегментов и требует отдельной
  проверки совпадения рамок с кадром.
  Рамок в реальном времени нет — то, что анализ видит на последнем кадре (`/api/live`, опрос раз в 2 секунды).
  Рамки выключаются переключателем над стеной, выбор запоминается.
- **Добавление камеры** (руководитель проекта и администратор): производитель или ручной RTSP-адрес, IP, логин,
  пароль → «Проверить и показать видео»; форма показывает живое видео до сохранения. Без кадра показывается
  нейтральный статус вместо нарисованной стройплощадки.
- **Опция Spider при создании/изменении камеры** — отдельный переключатель для видеокадров этой камеры: новые
  камеры создаются с выключенной опцией, существующие сохранили прежнее включённое состояние. Добавление камеры
  доступно руководителю и администратору, изменение существующей — администратору.

## Оформление

Светлая и тёмная темы плюс режим «как на устройстве» (по умолчанию). Переключатель — значок в верхней панели и на экране входа.
Цвета в компонентах задаются только токенами из `src/index.css`, тёмная тема — переопределение тех же токенов.

## Что показывает интерфейс (по ТЗ)

- **Обнаружение техники** — рамки с типом и уверенностью поверх живого видео (`video/TrackBoxes` — в реальном времени, иначе `video/DetectionBoxes`) и на кадрах-доказательствах (`CameraFrame`, `AnalyzeView`).
- **Сопоставление с графиком** — «нужно по плану / видим на камерах» (`EquipmentCheck`, считает сервер) и календарный план
  (`StageTimeline`): завершённые, текущие и будущие этапы; у текущих на полосе — сколько сделано по факту и где работы
  должны быть по графику на сегодня, отставание в днях, нужная техника. Отставание одинаково считается у работы, этапа
  и всего объекта (`lib/schedule.ts`): то, что сделано сейчас, по графику должно было быть готово N дней назад.
- **Работы по камерам** (`WorkByCameras`, на странице объекта) — ответы «по технике» и «по снимку (ИИ)» рядом;
  возможное начало следующей работы и отставание показываются отдельно. Опрос каждые 5 секунд во время анализа,
  иначе раз в минуту. Ошибка чтения не скрывает карточку: можно повторить GET без нового платного анализа.
- **Фотоанализ** (вкладка объекта и экран «Проверить фото») — загруженное фото анализируется отдельно от камер:
  реальное CV, локальный план и история идут обоим сервисам; Spider по выбору дополняет только плановый контекст.
  Одновременно к `vlm_llm` отправляется не более трёх запросов от камер и фото; при очереди интерфейс показывает
  предупреждение подождать. Фото и ответы доступны только пользователям с доступом к объекту.
- **Ресурсы Spider по кадру** (`ResourceAssessment`) — если выбран Spider и есть успешный импорт, оба сервиса
  получают v2; deterministic показывает статус оценки, причины, плановые и видимые количества, допустимую
  разницу и ссылки на сохранённые доказательства, VLM не делает числовой расчёт. Без достоверного охвата,
  сопоставления этапа/классов или при демонстрационном источнике цифры не объявляются производственным отставанием.
  Отсутствие открытых замечаний означает только пустой журнал, не подтверждение графика. Без текущего этапа
  плитка готовности и общий план показывают «сейчас нет этапа по плану», сохраняя числовые проценты.
- **Подключение Spider** на вкладке «План работ» — руководитель/администратор задаёт origin и токен для конкретного
  объекта, затем запускает импорт. Сохранённый токен не возвращается браузеру; при смене origin старые данные источника
  не используются.
- **Выявление отклонений** — карточка с кадрами-доказательствами, блоком «Почему система так решила»
  (план → правило → кадры → вывод), подсказкой «Что делать» и кнопкой «Смотреть камеру сейчас» (`AlertDetail`).
- **Живые данные** — видео в реальном времени, рамки 5–8 раз в секунду от модели на сервере (без них — раз в 2 секунды),
  предупреждения подтягиваются каждые 20 секунд;
  сверку с планом сервер делает сам раз в минуту.

## Структура

```
src/
  api/          клиент API: адреса, токен (в том числе продление токена Keycloak), ошибки понятными словами;
                openapi.d.ts — типы из схемы бэкенда (npm run gen:api), contract.ts сверяет с ними data/types.ts
  store/        состояние приложения: вход, данные с сервера (TanStack Query), действия
  data/         типы (совпадают с JSON бэкенда), подписи ролей, названия и цвета техники
  components/   video/ (VideoWall, VideoTile, CameraViewer, TrackBoxes/LiveBoxes, DetectionBoxes),
                camera/ (добавить, изменить камеру, адрес потока, проверка связи), site/ (объект, план, зоны, удаление),
                AlertCard, AlertDetail, PrescribeDialog, CameraFrame, EquipmentCheck, WorkByCameras, StageTimeline, AnalyzeView,
                ErrorBoundary, ui/* (в том числе ActionMenu — меню «⋯»)
  pages/        экраны по ролям: foreman/, manager/, inspector/, admin/ (Manage — Сотрудники, Правила, Журнал),
                shared/ + Login, MinimalDemo, Help
  lib/          видео (HLS на публичном HTTPS, WHEP локально, видимость плиток), рамки в реальном времени (useTracks),
                опрос /api/live, отставание в днях (schedule), советы по ролям (alertAdvice), состояние в адресе (useUrlState), даты по Москве, подписи
  test/         заготовки данных для тестов (*.test.ts лежат рядом с кодом, npm test)
e2e/            смоук-тесты Playwright по ролям (npm run test:e2e, настройки — playwright.config.ts)
```

## Стек

Vite · React 19 · TypeScript · Tailwind CSS 4 · TanStack Query · framer-motion (только функциональные анимации; компоненты `m.*`
в `LazyMotion` — сами анимации подгружаются после первого экрана, см. `lib/motionFeatures.ts`) ·
lucide-react · react-router · keycloak-js · Golos Text (self-hosted). Дизайн-решения: `../design-system/stroymonitor/pages/app.md`.
