# СтройКонтроль

Сервис поиска нарушений на строительных площадках Москвы по видео с камер. Прототип для хакатона «Лидеры цифровой
трансформации 2026» (задача Департамента градостроительной политики Москвы), команда «Работяги».

**Как работает:** видео камеры → техника на кадре (своя модель YOLO прямо на сервере) → сверка с календарным планом
по правилам «этап работ → необходимая техника» → понятное предупреждение с зоной и кадрами-доказательствами.

> **Состояние на 28 сентября 2026 г.** Четыре функции минимального прототипа подтверждены на одном живом
> сценарии «камера → CV → правило → отклонение с кадрами → обработка». Активный tracker использует
> `yolo26m-multiscale-v1` с восемью сопоставленными классами; точность на независимой разметке не измерена.
> «Работы по камерам» используют supplied Docker-комплект аналитики 0.5.0: без Spider оба сервиса получают
> vendor v1, после успешного импорта и явного выбора контекста — resource-v2 с проверкой возможностей каждого
> получателя. Два последних контролируемых VLM-запроса вернули 502 (`model_invalid_response`); работа этой ветви
> пока не подтверждена. Без Docker доступна строгая v1-имитация.

## Подробно по частям

### Видео с камер — готово

- Камеры подключаются по RTSP: форма «Добавить камеру» с производителями и проверкой связи, предпросмотр видео перед
  сохранением. Пароль камеры остаётся на сервере и в шлюзе, в браузер он не попадает.
- Шлюз видео mediamtx забирает RTSP с камер и отдаёт браузеру WebRTC с задержкой около 0,5 с. Потоки камер в шлюзе
  заводит сам сервер, и он же решает, кому какую камеру можно смотреть.
- Автоматическая публикация всех роликов Wikimedia Commons по-прежнему включается только в явном стендовом режиме
  (`SK_DEMO_MODE=true`). В рабочем режиме одну выбранную запись можно отдельно включить как обычную камеру — см. ниже.
- Видеостена и просмотр камеры на всю вкладку; видео подключается, только пока плитка видна на экране.

### Локальная запись вместо камеры (Docker, без демо-режима)

После запуска сайта из каталога `Hakaton-main`:

```bash
docker compose --env-file .env -f replay.compose.yml up -d
```

По умолчанию по кругу и в реальном времени воспроизводится `backend/app/assets/clips/foundation-mixer.mp4`. Чтобы взять свой файл, укажите его абсолютный путь **на этом компьютере** и пересоздайте только ретранслятор:

```bash
REPLAY_VIDEO_FILE=/absolute/path/to/recording.mp4 docker compose --env-file .env -f replay.compose.yml up -d --force-recreate
```

Другие сервисы и данные сайта эта команда не перезапускает. Совместимое H.264-видео передаётся без перекодирования; остальные форматы преобразуются в H.264 до 720p/30 кадров в секунду, звук не используется. Ретранслятор стартует вместе с Docker и остаётся отдельным от `SK_DEMO_MODE` и наполнения базы.

Добавьте обычную камеру на нужный объект: в разделе **Камеры → Камера на этот объект** создайте **рабочую зону**, укажите `video` как адрес, `8554` как порт, `/replay-local` как путь, `sk-replay` как логин. Получить ограниченный пароль только для чтения/публикации `replay-*` можно командой:

```bash
docker compose --env-file .env -f replay.compose.yml exec replay /app/.venv/bin/python -c "from app.services.video import replay_password; print(replay_password())"
```

Нажмите **Проверить и показать видео**, убедитесь в движущемся предпросмотре и сохраните камеру. Видео для браузера идёт через обычный защищённый `cam-*`-путь; ретранслятору недоступны чужие камеры. Чтобы заменить запись, оставьте путь `/replay-local` прежним: камера продолжит работать без изменения адреса. Остановить только воспроизведение: `docker compose --env-file .env -f replay.compose.yml stop replay`; вновь запустить: `docker compose --env-file .env -f replay.compose.yml start replay`.

На вкладке **Фотоанализ** галочка Spider изначально снята; при необходимости её можно включить для отдельного фото.

### Второй учебный объект: отставание дорожных работ

Объект `s_8561989e6d` — «Демо — дорожные работы (отставание)». План на 21.09–04.10.2026:
подготовка основания 21–24.09 отмечена выполненной на 100%; уплотнение верхнего слоя основания
25.09–01.10 отмечено на 0%; устройство верхнего слоя покрытия запланировано на 02–04.10.
На 28.09 интерфейс показывает факт объекта 29%, план 57% и отставание примерно на четыре дня.
Это **учебные отметки прогресса**, а не измерение выполненных работ по видеокадру.

Камера `cam_163889de3b` находится в зоне **въезда**, показывает движущуюся запись
`road-dumptruck.mp4` через `/replay-road-lag`. Активный tracker увидел самосвал; плановые
проверки учитывают его как прибывающий, но не как технику рабочей зоны. Машинное нарушение
для этого объекта не заявлено: на въезде нет покрытия рабочей зоны, а правило нехватки
техники в учебном плане не задано. Это не скрытая ошибка аналитики. Такая зона не
отправляет кадры в периодический VLM-анализ и не добавляет платных запросов.

Отдельный ретранслятор перезапускается из `Hakaton-main`, если его остановили:

```bash
REPLAY_PATH=replay-road-lag REPLAY_VIDEO_FILE="$PWD/backend/app/assets/clips/road-dumptruck.mp4" \
  docker compose -p stroykontrol-lag-road --env-file .env -f replay.compose.yml up -d
```

Штатный `./start-all.sh --gpu` не управляет этим отдельным Compose-проектом; его контейнер
имеет `restart: unless-stopped`. Для остановки только этой учебной камеры используйте
`docker compose -p stroykontrol-lag-road --env-file .env -f replay.compose.yml stop replay`.
Пароли камеры не приводятся; происхождение ролика — [CREDITS.md](backend/app/assets/clips/CREDITS.md).


### Распознавание техники — готово, ждём новую версию модели

- Модель **YOLO26m, дообученная на датасете MOCS** (Moving Objects in Construction Sites, 13 классов). На проверочной
  выборке при обучении mAP50 = 0,83, mAP50-95 = 0,66. Файл обучен 16.09.2026 — это старая версия; новую должен
  прислать разработчик модели.
- Модель считается прямо в бэкенде через ONNX Runtime, без PyTorch; файл — 41 МБ
  ([backend/models/detector.onnx](backend/models/)). Время на кадр: на Mac с M4 через CoreML около 35 мс,
  на процессоре около 70 мс, в Docker на том же Mac около 0,2 с.
- Ответы сервера совпадают с исходной моделью в Ultralytics на всех 13 демо-фото.
- Кадр с каждой камеры разбирается раз в 2 секунды; раз в минуту объект сверяется с планом. Отклонение
  подтверждается на 2–3 сверках подряд, поэтому предупреждение появляется через 2–3 минуты, а одиночная ошибка
  распознавания его не вызывает.
- Какие классы модели считаются какой техникой:

  | Класс MOCS | Техника ТЗ |
  |---|---|
  | Excavator | экскаватор |
  | Truck | самосвал (отдельного самосвала в MOCS нет, Truck там — почти всегда самосвалы) |
  | Roller | каток |
  | Bulldozer | бульдозер |
  | Crane | автокран |
  | Concrete mixer | бетоносмеситель |
  | Worker, Static crane, Hanging head, Loader, Pump truck, Pile driving, Other vehicle | не техника ТЗ — не показываются |

- **Ограничение:** кран-манипулятор и грузовик модель не знает. Если у новой версии классы будут называться иначе,
  соответствие задаётся настройкой `SK_DETECTOR_CLASSES` без правки кода.
- **Новая версия модели** — одна команда: `tools/export_model.py` переводит `.pt` от Ultralytics в ONNX и сверяет ответы
  с исходной моделью (подробно — [backend/README.md](backend/README.md#своя-модель)).
- Модель обучена в Ultralytics, лицензия — AGPL-3.0.

### Рамки техники на видео в реальном времени — готово

- Модель разбирает видео только тех камер, которые сейчас открыты на экране: на M4 с CoreML — 6–8 раз в секунду
  на камеру, если открыты одна-две камеры, и около 4 раз, если семь. Камеры, которые никто не смотрит, получают рамки
  из обычного анализа раз в 2 с.
- Номер машины между кадрами даёт простой трекер. Браузер плавно ведёт рамку за техникой и придерживает видео
  на 150 мс, чтобы рамка попадала в машину.
- Внешний сервис разметки (WebSocket) остался запасным вариантом — например, для отдельного компьютера с видеокартой.
  Его контракт и имитация описаны в [backend/README.md](backend/README.md#рамки-техники-в-реальном-времени).

### Сверка с планом и отклонения — готово

- Методика — 9 правил «этап → техника»: какая техника нужна, в каком количестве и какой быть не должно, с объяснением
  риска. Правила меняет администратор.
- Техника в рабочих зонах засчитывается в норму, а на въезде и складе считается подъезжающей.
- Виды отклонений:
  - нет нужной техники;
  - техники меньше нормы;
  - техника не по этапу;
  - простой: техника стоит 2 часа и дольше;
  - камера не отвечает.
- В каждом отклонении есть зона, кадры-доказательства, блок «Почему система так решила» (план → правило → кадры →
  вывод) и совет, что делать.
- Путь отклонения: «Новое» → «В работе» → «Подтверждено» → «Предписание» (форма с требованием и сроком устранения) →
  «Устранено». Ложное срабатывание отмечается как «Ошибка системы». Предписания выдают и закрывают инспектор
  и администратор.
- Выполнение работ по факту отмечают руководитель проекта и администратор. Прораб видит план и выполнение, но не
  отмечает его.

### Работы по камерам — сервисы аналитики коллеги

- Какая работа **локального** плана идёт на кадре, определяют два сервиса: **«по технике»** (матрица
  «техника → вид работ», история, отметки выполнения) и **«по снимку»** (VLM→LLM смотрит кадр).
- Раз в 20 минут сервер отправляет свежий кадр каждой камеры рабочей зоны, технику от нашей модели, план объекта с
  видами работ по справочнику сервисов и историю наблюдений за неделю (без картинок). Руководитель и администратор
  могут отправить сейчас кнопкой «Определить сейчас». Импорт Spider сам по себе не запускает анализ и не добавляет
  платных модельных вызовов.
- Без успешного импорта Spider оба сервиса получают vendor `frame-analysis-input-v1`. После успешного site-scoped
  импорта оба сервиса получают закрытый vendor `frame-analysis-input-v2` для камер с включённой опцией Spider либо
  для независимого фото, если при загрузке выбрана эта опция. Возможности каждого получателя проверяются отдельно;
  при отсутствии v2 контекст не удаляется и повторного POST v1 нет. Старый custom-v2 с `spider_context` не
  совместим с получателем 0.5.0 и не отправляется.
- Обязательная resource-v2-надстройка — `analysis_mode`, `source_context` (`source_system`, ID снимка, `source_ref`,
  `data_type`, качество времени и признак live sync), `resource_plan`, `resource_target` и
  `equipment_observation`. `resource_plan.stages` передаёт внешний код, имя, порядок, сроки, source ref, статус
  сопоставления/разрешённые local step keys, смены, объём, производительность и строки техники с количеством. Это
  плановый контекст: VLM возвращает `resource_assessment = not_evaluated`, а не вычисленный факт работ.
- В v2 не передаются фотографии, observations, ручные counts/annotations, готовые сравнения, документы, URL или
  токены Spider. `equipment_observation` описывает только тот же локальный CV кадра либо его недоступность; Spider не
  становится зрительным свидетельством и не заменяет локальный план. Коды и названия его этапов не сопоставляются
  автоматически и не расширяют допустимые работы на кадре.
- Если поздний импорт не удался или истёк refresh, сайт использует последний успешный план и показывает локальный
  признак stale, не подменяя `source_snapshot_id` текущим источником. `synthetic_demo` и ограничения сопоставления
  остаются provenance/неопределённостью.
- У двух фактических отправок разные request ID и точные metadata/fingerprint, даже если кадр один. При отсутствии
  `/v2/analyze/frame` контекст не удаляется и не повторяется как v1: результат сообщает о несовместимости контекста.
- На странице объекта ответы обоих сервисов стоят рядом, по каждой камере: какая работа (или «одна из»), что видно
  на снимке и почему так, сопоставлена ли работа с локальным планом. Отдельно — «похоже, началась следующая работа»
  и «возможное отставание» по отметкам выполнения; оценки ресурсов показываются для конкретного кадра с
  provenance и границами сопоставления. Одного «победителя» не выбираем, отметки выполнения по ответам не меняются.
- Руководитель и администратор задают origin и токен Spider **на вкладке «План работ» каждого объекта**, запускают
  импорт, а при создании или изменении камеры выбирают, передавать ли этот дополнительный контекст с её видеокадрами.
  Новый адрес или токен источника не наследует прежние импорты и подготовленные фото: нужен новый импорт и подготовка
  фото для текущего подключения. Spider не передаёт ID объекта, поэтому принадлежность внешнего плана объекту
  отмечена в интерфейсе как неподтверждённая. Загрузка независимой фотографии вынесена во вкладку
  «Фотоанализ»: фото не привязано к видеокамере и не меняет её состояние; локальное CV, план и история проходят через
  те же сервисы, а Spider включается для фото отдельно. Результаты и снимки доступны только участникам объекта.
- У каждой работы плана руководитель выбирает **вид работ по справочнику сервисов** — сопоставлять по похожему
  названию нельзя. Виды объектов теперь те же, что в «Справочнике видов работ» организаторов: жильё, школа, детский сад,
  больница… дороги. Работы без техники (геодезия, отселение) тоже можно выбрать — по ним сервисы следят только за
  сроками и отметками выполнения, по кадрам их не определяют.
- Настоящий получатель — supplied `service-release_1/service-release` с
  `lct-analytics-deterministic:0.5.0` и производным
  `lct-analytics-vlm-llm:0.5.0-spider` (поверх vendor `lct-analytics-vlm-llm:0.5.0`);
  подключение использует `DETERMINISTIC_SERVICE_URL`, `VLM_LLM_SERVICE_URL` и
  `ANALYTICS_SERVICE_TOKEN`. `LITELLM_API_KEY` остаётся только у аналитического сервиса. Подробные запуск,
  проверка поставки и предел smoke-проверки — [в README бэкенда](backend/README.md#работы-по-камерам-сервисы-аналитики-коллеги-frame-analysis-v1-и-v2).
- **Без Docker — строгая v1-имитация** (`backend/app/mock_analytics.py`): она подходит для обычного анализа и не
  имитирует Spider-контекст.

### Интерфейс — готово

- **Прораб** (в основном с телефона): «Сегодня» — что не так на его объекте, камеры, план работ.
- **Руководитель проекта:** все объекты со «светофором», страница объекта (сегодня с «работами по камерам», камеры,
  план), отклонения, отчёт, проверка фото. Заводит объекты, зоны и план (у работ — вид работ по справочнику сервисов
  аналитики; план можно загрузить из Excel или CSV по шаблону), отмечает выполнение, подключает камеры.
- **Инспектор:** журнал нарушений с поиском и выгрузкой в Excel, предписания, отчёт.
- **Администратор:** всё то же, а также сотрудники и их пароли, правила «этап → техника» (добавить, изменить,
  удалить), журнал действий.
  Изменить, проверить и удалить камеру может только администратор. Выключать камеры нельзя никому.
- Для загрузки отдельного настоящего фото служит «Фотоанализ» на странице объекта; публичных примеров в интерфейсе нет.
- Простой интерфейс для людей без опыта работы с компьютером: крупные кнопки (не меньше 44 px), простые слова,
  подтверждение каждого действия, тёмная тема и режим «как на устройстве».

### Данные и хранение — готово

- Локально — SQLite, в Docker — PostgreSQL. Структура базы — миграции Alembic; сервер применяет их при запуске.
- Новая база по умолчанию содержит только базовую методику «этап → техника» (9 правил): никаких сотрудников,
  объектов, камер и снимков. Первого администратора создают отдельно. Демонстрационное наполнение теперь
  только явное: `SK_DEMO_MODE=true SK_SEED_ON_START=true`; старую базу при старте не очищаем.

## Что нужно до работы на настоящей стройке

Для показа на демо-данных всё работает. Для настоящей стройки уже сделано:

- **Рабочее время объекта** (часы и дни в карточке объекта). Вне его технику не сверяем — ночью и в выходные нет
  ложных «нет экскаватора» и «простой», кадры сервисам аналитики тоже не уходят.
- **Техника, которую модель не распознаёт** (кран-манипулятор, грузовик): её нехватка не становится отклонением —
  система пишет «проверьте на месте».
- **Правила «этап → техника» есть в любой новой базе**, не только в демо: базовая методика из 9 правил ставится сама.
  Администратор добавляет, переименовывает и удаляет правила в интерфейсе.
- **«По снимку» — реже и с ограничением:** сервис «по технике» — раз в 20 минут, «по снимку» — раз в час;
  одновременно выполняется не более трёх LLM-анализов от камер и фото. Остальные ждут, интерфейс просит
  дождаться предыдущих анализов.
- **Запуск без демо-данных:** первого администратора создают `uv run python -m app.manage create-admin`; пустые
  экраны подсказывают последовательность: объект → план и зоны → камеры.
- **План из Excel или CSV:** шаблон со списками правил и видов работ для объекта, предпросмотр с ошибками по номерам
  строк файла, загрузка — только когда ошибок нет; можно дополнить план или заменить его.

Что ещё осталось: **активная модель не проверена на независимой размеченной выборке** для восьми классов и
разнообразных условий. Mapping заявляет все восемь, но успешный кадр не доказывает точность. Внешний Spider
вернул демонстрационный (`synthetic_demo`) план ресурсов; плановые объёмы не выдаются за факт. Исторически
VLM→LLM отвечал HTTP 200 на отдельное фото, но два последних контролируемых анализа камеры и фото дали 502
(`model_invalid_response`). До исправления и повторной проверки нельзя заявлять стабильный VLM-путь.

## Что осталось до финальной сдачи

- Новая версия модели от разработчика модели, лучше с кран-манипулятором и грузовиком. Подключается одной командой.
- Сервисы аналитики коллеги: проверка на реальных кадрах и договорённость о частоте вызовов «по снимку» (они платные).
- Презентация (.pptx / .pdf) и документация (.doc / .pdf) — по разделам 4 и 5 ТЗ.
- Прототип, доступный жюри по ссылке, и открытый репозиторий (сейчас он приватный).

## Запуск

**Docker — всё сразу: PostgreSQL, шлюз видео, API, интерфейс:**

```bash
docker compose up --build        # интерфейс: http://localhost:8080 · API и Swagger: http://localhost:8100/docs
```

До запуска задайте случайный `SK_SECRET_KEY` в `Hakaton-main/.env`; после запуска создайте администратора:
`docker compose exec backend /app/.venv/bin/python -m app.manage create-admin --login admin --name "Фамилия Имя"`.
Новая база не содержит демо-записей. Если старый стенд уже использует `hakaton-main_pgdata` и
`hakaton-main_media`, задайте в `.env` новые `SK_DB_VOLUME` и `SK_MEDIA_VOLUME` для чистой установки:
старые тома, включая загруженные ранее фото и импортированные данные, останутся нетронутыми. Не используйте
`docker compose down --volumes` для очистки старого стенда.

Вход через Keycloak включается отдельно: укажите `SK_KEYCLOAK_ISSUER` (полный URL realm, доступный и браузеру,
и контейнеру backend) и `SK_KEYCLOAK_CLIENT_ID` в `.env`, затем перезапустите backend. При необходимости управления
сотрудниками из интерфейса добавьте `SK_KEYCLOAK_ADMIN_CLIENT_SECRET` действующего служебного клиента.
Без настроенного issuer интерфейс показывает локальный вход; демо-Keycloak из `infra/keycloak` содержит тестовые
учётные записи и не подходит для рабочего сайта.

Для настоящих сервисов из корня репозитория есть единый безопасный запуск: он сначала проверяет supplied комплект
analytics 0.5.0 и поднимает его получатель, затем стенд и **ровно один** внешний YOLO-трекер. По умолчанию выбран GPU;
для CPU укажите `--cpu`. Он закрепляет существующие Compose projects/volumes analytics и сайта (`lct-analytics-release`
и `hakaton-main`), игнорирует унаследованный `COMPOSE_PROJECT_NAME`, не удаляет контейнеры или named volumes и не
меняет порты, заданные в Compose.

Получатель первым создаёт сеть `lct-analytics-release_default`. Локальный overlay
[`analytics-network.compose.yaml`](analytics-network.compose.yaml) подключает только `backend` также к этой внешней
сети: он обращается к `http://deterministic:8000` и `http://vlm_llm:8000` по service DNS. `db`, `video`, `frontend`,
встроенный mock `analytics` и YOLO-трекер остаются только в стандартной сети сайта. Опубликованные порты analytics
остаются привязанными к `127.0.0.1`; соединение backend→analytics не проходит через host bridge или опубликованный порт.

Перед запуском заполните игнорируемый `service-release_1/service-release/.env` настоящими `POSTGRES_PASSWORD`,
`ANALYTICS_DETERMINISTIC_DB_PASSWORD`, `ANALYTICS_VLM_DB_PASSWORD`, `ANALYTICS_SERVICE_TOKEN` и
`LITELLM_API_KEY`; в `yolo_service/.env` укажите настоящий `SK_TRACKER_API_KEY` и существующий абсолютный
`YOLO_MODEL_HOST_PATH`. В `Hakaton-main/.env` обязателен случайный `SK_SECRET_KEY` и для скрипта —
`CAMERA_STAGE_MONITOR_URL`; `CAMERA_STAGE_MONITOR_TOKEN` необязателен. Скрипт берёт общий analytics-токен
только из `service-release_1/service-release/.env`, передаёт его обоим стекам и сам выставляет внутренние URL analytics
и YOLO, не печатая секреты.

```bash
./start-all.sh --check  # SHA256SUMS/manifest, prerequisites и docker compose config; контейнеры и образы не меняются
./start-all.sh          # только после проверки миграции отправителя: загрузка 0.5.0 → analytics → site + GPU YOLO
./start-all.sh --cpu    # то же, но только CPU-трекер
```

`--check` проверяет поставленный `service-release_1/service-release` (archive SHA-256 и manifest), его
`compose.yaml`, внешнюю сеть analytics и итоговый site+network-overlay+YOLO Compose до `docker load` или запуска.
Стандартный том базы сайта — `hakaton-main_pgdata`; при `SK_DB_VOLUME` используйте отдельный чистый том.
Секреты читаются только из соответствующих `.env`. Обычный запуск после проверок загружает архив, сверяет
manifest ID обоих образов `linux/amd64`, поднимает analytics (и его сеть), а затем site; `down`, удаление и
пересоздание volume он не выполняет.

Без настоящего ключа LiteLLM, адреса Camera Stage Monitor, analytics-реквизитов, ключа/файла модели YOLO скрипт
завершается до `docker load` и `docker compose up`. Полная последовательность и проверка 0.5.0-поставки —
[README бэкенда](backend/README.md#работы-по-камерам-сервисы-аналитики-коллеги-frame-analysis-v1-и-v2).

Без комплекта — с имитацией обоих сервисов:

```bash
DETERMINISTIC_SERVICE_URL=http://analytics:8300/deterministic VLM_LLM_SERVICE_URL=http://analytics:8300/vlm_llm docker compose --profile analytics up --build
```

В Docker модель считает только на процессоре (около 0,2 с на кадр на Mac с M4). Для показа на Mac бэкенд лучше
запускать без Docker — тогда модель считает через CoreML, примерно в 6 раз быстрее.

**Локально — три терминала** (нужны `uv`, Node.js, `brew install ffmpeg mediamtx`):

```bash
cd backend && uv sync && uv run uvicorn app.main:app --port 8100
```

```bash
bash tools/video-gateway.sh      # шлюз видео mediamtx: RTSP с камер → WebRTC в браузер
```

```bash
cd frontend && npm install && npm run dev     # http://localhost:5180
```

Сервисы аналитики: настоящий получатель — адреса `http://127.0.0.1:18001`, `http://127.0.0.1:18002` и токен кладутся
в `backend/.env` (в git не попадает); supplied 0.5.0 запускается из
`service-release_1/service-release/compose.yaml` с поддерживаемым Spider overlay
`analytics_service_05/compose.override.yaml`, который использует
`lct-analytics-vlm-llm:0.5.0-spider`. Или используется строгая v1-имитация —
`uv run --directory backend uvicorn app.mock_analytics:app --port 8300` и бэкенд с
`DETERMINISTIC_SERVICE_URL=http://127.0.0.1:8300/deterministic`, `VLM_LLM_SERVICE_URL=http://127.0.0.1:8300/vlm_llm`.

**Вход:** в чистой установке — логин и пароль созданного администратора; остальных сотрудников он добавит
в разделе «Управление». Вход через Keycloak описан в [README бэкенда](backend/README.md#вход-через-keycloak-необязательно).

## Как это устроено

```
камера (RTSP) ──► шлюз видео ──► браузер: живое видео (WebRTC) + рамки техники
                     │                         ▲ рамки в реальном времени (WebSocket)
                     ├──► сервер: видео камер, которые смотрят ──► модель YOLO ──┘
                     │
                     └──► сервер: кадр каждые 2 с ──► модель YOLO ──► техника на кадре
                                                                        │
                          раз в минуту: сверка с правилом этапа по плану ◄┘
                                         └──► предупреждение с зоной и кадрами-доказательствами

                          раз в 20 минут: кадр камеры + техника + план + история ──► сервисы аналитики коллеги
                                         └──► «работы по камерам»: «по технике» и «по снимку» рядом с графиком
```

Управление — там, где список: объекты добавляются в списке объектов, их план, зоны и удаление — на странице объекта,
