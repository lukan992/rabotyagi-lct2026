# SPEC.md

## 1. Обзор технической реализации

`Hakaton-main/backend` — FastAPI и SQLAlchemy; локально SQLite, в Compose PostgreSQL. `Hakaton-main/frontend` — React/TypeScript. MediaMTX принимает RTSP, backend или внешний YOLO tracker получает кадры, backend сохраняет снимки и детекции, движок сверяет их с планом. `analytics_service_05` и `service-release_1` содержат отдельный контур анализа работ. `camera_overlap_module` — локальный SuperPoint + LightGlue с HTTP-адаптером для попарной оценки видимых областей.

## 2. Структура проекта

- `Hakaton-main/backend/app/api/` — HTTP-маршруты сайта; `services/` — видео, сверка, аналитика и пересечения.
- `Hakaton-main/backend/migrations/` — изменения схемы БД; `tests/` — проверки API и логики.
- `Hakaton-main/frontend/src/` — интерфейс и типы контракта.
- `yolo_service/` — внешний tracker, передающий кадры и детекции в backend.
- `camera_overlap_module/src/camera_overlap/` — самостоятельный пакет и локальные веса; `service.py` — HTTP-адаптер; `Dockerfile.service` — сервисный образ.

## 3. Схема взаимодействия компонентов

`RTSP → MediaMTX → backend/YOLO tracker → Snapshot + Detection → сверка объекта`.

Отдельный фоновый цикл: `Snapshot двух камер одного Site → POST camera-overlap /analyze → camera_overlaps → матрица API → приблизительная оценка в equipment-check`.

Анализ пересечений идёт вне минутной сверки. Сервис загружает веса один раз при запуске. Backend повторно использует сохранённый результат для неподвижной пары камер.

## 4. Запуск проекта

Из `Hakaton-main`: задать `SK_SECRET_KEY` в `.env`, затем `docker compose up --build`. Compose поднимает PostgreSQL, MediaMTX, backend, frontend и внутренний `camera-overlap` на CPU; порт сервиса пересечений наружу не публикуется. У backend адрес сервиса — `http://camera-overlap:8000`.

Для локального запуска backend: `cd Hakaton-main/backend`, `uv sync`, затем `uv run uvicorn app.main:app --port 8100`. Отдельно запустить сервис пересечений с зависимостями из `camera_overlap_module/pyproject.toml` и `fastapi`, `uvicorn`, `python-multipart`: `uvicorn service:app --app-dir ../../camera_overlap_module --port 8000`, задав `SK_OVERLAP_SERVICE_URL=http://127.0.0.1:8000` backend. При пустом URL поиск пересечений отключён. Миграции применяются backend при старте.

## 5. API и интерфейсы

Публичные маршруты сайта расположены под `/api`; JWT и доступ к объекту проверяются backend. Полный актуальный список, схемы запросов и ошибок доступен в `/openapi.json`.

| Метод и путь | Вход | Выход и ошибки | Доступ |
|---|---|---|---|
| `GET /api/sites/{site_id}/camera-overlaps` | ID объекта | `cameras`, квадратная `matrix` статусов и `pairs` с областями/геометрическими метриками; 404/403 для недоступного объекта | Участник объекта |
| `POST /api/sites/{site_id}/camera-overlaps/recompute` | JSON `{camera0Id, camera1Id}` | Повторный реальный анализ одной пары; 404 при отсутствии камер/кадров, 503 при отключённом или ошибочном сервисе | Руководитель/администратор |
| `GET /api/sites/{site_id}/equipment-check` | ID объекта | Обычная сверка, `estimatedObserved` для рабочей зоны, `estimatedSiteObserved` для всех зон (словари или `null`), `overlapMatches`; 404/403 | Участник объекта |
| `POST camera-overlap /analyze` | multipart `image0`, `image1`, необязательный `X-Overlap-Token` | JSON `camera-overlap-v1`; 401, 413, 422, 503 при соответствующей ошибке | Внутренний сервис |
| `GET camera-overlap /health/live` | — | `{status: "ok"}` | Внутренний сервис |

Другие группы API: авторизация, объекты/зоны/план, камеры/видео, снимки, приём кадра и детекций, предупреждения, отчёты, фотоанализ, аналитика работ и Spider. Их действующие контракты определены `app/api/`, `app/schemas.py` и генерируемым OpenAPI.

## 6. Pipeline обработки пересечений и счёта

1. Фоновый цикл раз в `SK_OVERLAP_SYNC_INTERVAL_SECONDS` перебирает уникальные пары активных камер внутри каждого объекта. Для невычисленной или устаревшей пары выбираются существующие JPEG, близкие по `taken_at`, из последних 12 снимков каждой камеры.
2. Backend читает локальные JPEG из `SK_DATA_DIR/media/frames/<camera_id>/`, отправляет два файла multipart в сервис и проверяет версию/структуру результата.
3. Сервис в отдельном потоке применяет SuperPoint + LightGlue и геометрический фильтр. `candidate_overlap` содержит области в пикселях каждого исходного JPEG и матрицу F; `insufficient_evidence` содержит причину отказа. Сервисная ошибка записывается и повторяется не раньше чем через пять минут. После трёх результатов `insufficient_evidence` автоматические попытки прекращаются до явного пересчёта или смены источника.
4. Backend сохраняет полный JSON результата в `camera_overlaps`. Результат кандидата используется до изменения RTSP-источника или явного пересчёта. Простое физическое перемещение без изменения адреса автоматически не определяется.
5. В `equipment-check` текущие детекции рабочих камер остаются основой правил и предупреждений. Отдельная оценка группирует рамки одинакового класса, если их нижние центральные точки лежат в обеих предлагаемых областях, времена кадров отличаются не более чем на 60 секунд, а симметричная эпиполярная ошибка не выше 25 пикселей. Сортировка по ошибке и объединение групп предотвращают повторное вычитание при трёх камерах. Алгоритм вызывается для рабочей зоны и для всех камер объекта (включая въезд и склад); оба результата приблизительны, при отсутствии пригодной пары соответствующее поле возвращает `null`.

## 7. Данные, БД и модели

`sites` объединяет `cameras` и `zones`. `snapshots` содержит `camera_id`, `site_id`, `taken_at`, `image_url`, детекции и необязательный `check_id`; сами кадры лежат в файловом томе. `camera_overlaps` (миграция 0013) имеет упорядоченную пару `camera0_id < camera1_id` как ключ, `site_id`, статус, JSON результата, ID использованных снимков без FK, отпечатки RTSP-источников, число попыток, время и ошибку. ID снимков остаются диагностическими после штатной очистки истории.

`equipment_visits` хранит track ID только в пределах камеры и tracker-сессии; глобального ID машины нет. `CheckRun.observed` и автоматические предупреждения пока сохраняют прежнюю сумму детекций по камерам.

## 8. Хранилище файлов и артефактов

В Docker `SK_DATA_DIR=/app/data` расположен в именованном томе `media`; JPEG — `media/frames/<camera_id>/`. Обычные снимки сверх `SK_KEEP_FRAMES_PER_CAMERA` удаляются, кадры-доказательства сохраняются. Результат пересечений хранится как JSON в БД и не зависит от срока хранения исходных JPEG. Веса SuperPoint и LightGlue входят в пакет `camera_overlap_module` и проверяются по SHA-256 при загрузке.

## 9. Переменные окружения

| Переменная | Где используется | Обязательность и значение |
|---|---|---|
| `SK_SECRET_KEY` | Backend JWT и шифрование | Нужен в рабочем запуске; пример в `Hakaton-main/backend/.env.example` |
| `SK_DATABASE_URL`, `SK_DATA_DIR` | Backend БД и файлы | Есть локальные defaults; Compose задаёт PostgreSQL и том |
| `SK_FRAME_INTERVAL_S`, `SK_CHECK_INTERVAL_S`, `SK_KEEP_FRAMES_PER_CAMERA` | Видеоконвейер и очистка | Необязательны; defaults `2`, `60`, `200` |
| `SK_OVERLAP_SERVICE_URL` | Backend отправка пары | Необязателен; пусто — отключено; Compose `http://camera-overlap:8000` |
| `SK_OVERLAP_SERVICE_TOKEN`, `OVERLAP_SERVICE_TOKEN` | Общий токен backend/сервиса | Необязателен в закрытой Compose-сети; значения должны совпадать |
| `SK_OVERLAP_TIMEOUT_SECONDS`, `SK_OVERLAP_SYNC_INTERVAL_SECONDS` | Backend запрос/фоновый цикл | Необязательны; defaults `120`, `120` секунд |
| `OVERLAP_DEVICE` | Сервис Torch | `cpu` по умолчанию; `cuda` при совместимом образе/устройстве |

Другие переменные описаны в `Hakaton-main/backend/.env.example`; реальные секреты не входят в документацию.

## 10. Интеграции

MediaMTX передаёт RTSP; YOLO tracker при push-режиме присылает JPEG и детекции в `/api/ingest/snapshots`. PostgreSQL или SQLite хранят метаданные. Сервис пересечений использует локальные Torch, SuperPoint и LightGlue без сетевого вызова модели. Аналитические сервисы работ и Spider независимы от оценки пересечений.

## 11. Ошибки и ограничения

Поиск пересечений эвристический: повторяющиеся фасады дают ложные области, а `insufficient_evidence` не доказывает отсутствия пересечения. Две рамки в общей области могут относиться к разным машинам. Времена кадров — время получения RTSP, не синхронизированные аппаратные метки; предел 60 секунд допускает ошибку на движущейся технике. Области не являются картой земли, метровой площадью или калибровкой камер. Приблизительная оценка не управляет предупреждениями.

## 12. Нерешенные технические вопросы

- Требует уточнения: метрики на размеченных парах реальных строительных камер и допустимые пороги для межкамерного сопоставления.
- Требует реализации для точного учёта: проверенная калибровка общей рабочей поверхности и/или межкамерная идентификация машин с синхронизированными наблюдениями.
