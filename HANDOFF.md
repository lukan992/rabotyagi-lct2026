# Handoff: пересечения камер и сервис определения этапа

## Состояние на 2026-09-29

Рабочая ветка — `zone_fix`, базовый коммит реализации — `8d1d0fc`. Этот файл описывает состояние кода на момент передачи задачи. Код интеграции с сервисом определения этапа **ещё не изменён**.

### Уже реализовано

- `camera_overlap_module/service.py` принимает два изображения через `POST /analyze` и запускает локальный SuperPoint + LightGlue. `Hakaton-main/docker-compose.yml` поднимает сервис внутри сети Compose.
- `Hakaton-main/backend/app/services/camera_overlaps.py` выбирает сохранённые JPEG двух активных камер одного объекта, отправляет их сервису и сохраняет ответ в таблице `camera_overlaps` (миграция `0013_camera_overlaps.py`). Результат повторно используется для неподвижных камер; смена RTSP-источника делает его устаревшим.
- `GET /api/sites/{site_id}/camera-overlaps` отдаёт квадратную матрицу статусов и геометрию пар; `POST .../recompute` запускает явный пересчёт пары.
- `Hakaton-main/backend/app/services/overlap_count.py` на текущих детекциях оценивает число уникальных машин по классу, общим областям, близости времени и эпиполярной геометрии. `GET /api/sites/{site_id}/equipment-check` отдаёт `estimatedObserved` для рабочей зоны и `estimatedSiteObserved` для всех зон. В интерфейсе число помечено «неточно».
- Автоматическая сверка правил и предупреждения по-прежнему используют исходные детекции камер. Это осознанное ограничение приблизительной оценки.

### Текущий вход сервиса определения этапа

Сборка запроса находится в `Hakaton-main/backend/app/services/analytics/request.py`, отправка — в `client.py`. Один запрос содержит кадр **одной** камеры, его `cv.detections` с отдельными классами/рамками, локальный план и историю. `deterministic` считает технику по этим детекциям; `vlm_llm` анализирует изображение. Отдельного агрегата уникальной техники по объекту в запросе нет.

При наличии Spider используется vendor `frame-analysis-input-v2`. В текущем backend `equipment_observation.basis=cv_detections`, если CV успешно; `items=[]`. `resource_plan` может содержать **плановое** `planned_quantity`, но это не измеренное количество. По документу поставки `service-release_1/service-release/RESOURCE_INTEGRATION.md` ручной `manual_visual_estimate` допускается при недоступном/ошибочном CV, а при успешном CV основой остаются отдельные детекции. Поэтому помещать межкамерную оценку в `items` действующего контракта или создавать из числа фиктивные рамки нельзя.

**Разрыв интеграции:** результат `overlap_count.py` сейчас используется только в `equipment-check`; `analytics/request.py` его не читает и не передаёт обоим сервисам этапов. Изменение только backend без согласования и реализации у получателя нарушит vendor-схему v1/v2.

## Следующий шаг: согласовать и реализовать контракт

1. С владельцем сервиса этапов согласовать версионированный вход для **отдельной приблизительной оценки по объекту**. Нужно определить, использует ли её `deterministic` только как контекст в ответе или также при выборе этапа/ресурсном сравнении. До решения не менять действующую семантику `cv.detections`.
2. Указать в контракте класс и приблизительное количество, объект и область охвата (рабочая зона или все зоны), время и допустимое расхождение кадров, исходные камеры/снимки или ссылку на сохранённую матрицу, состояние качества (`неточно`, нет пригодной геометрии, устаревший результат). Не выдавать частичный охват за полный.
3. Обновить схему и валидацию на стороне сервиса, затем сборку запроса в `analytics/request.py` и проверку ответа в backend. Передавать поле только совместимому получателю с объявленной поддержкой; текущий v1 и существующий v2 должны продолжать работать по своим контрактам.
4. Определить, должен ли результат влиять на подсказку об этапе, на числовое сравнение с планом и на предупреждения. Сейчас разрешён только показ отдельной приблизительной оценки пользователю. В ответе сервиса сохранить происхождение оценки и её неопределённость.
5. Проверить сценарии: нет пары камер, `insufficient_evidence`, `service_error`, смена/перемещение камеры, несинхронные кадры, три камеры с одной машиной, частичный охват, несовместимый сервис, отсутствие Spider. Не подменять отсутствие оценки нулём или обычной суммой детекций.

### Что требует уточнения

- Должна ли межкамерная оценка менять **выбор этапа**, только ресурсное сравнение или оставаться дополнительным полем результата?
- Какой временной интервал и какой охват камер считать достаточными для передачи оценки как актуальной?
- Кто подтверждает, что предложенные области относятся к общей рабочей поверхности, а не к повторяющемуся фону?

## Проверка и ограничения текущей реализации

Новые тесты: `cd Hakaton-main/backend && uv run --locked --group dev pytest -q tests/test_camera_overlaps.py`. Проверены сборка frontend, миграция SQLite до `0013`, Compose config, Docker build и загрузка модели в образе. Полный backend suite на Windows имеет один ранее существовавший сбой POSIX-проверки прав файла; остальные тесты прошли.

Точность числа уникальных машин на камерах реального объекта ещё не измерялась. Сервис пересечений предлагает общую **видимую** область, а не калибрует площадку; совпадение рамок по геометрии не доказывает идентичность машины. Физическое перемещение камеры без смены RTSP-адреса требует ручного пересчёта.
